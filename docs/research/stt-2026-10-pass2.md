## CrispASR provenance (checked 2026-10-01)

This section is a check made by hand on 2026-10-01, after the research run above. It answers the open question on CrispASR. The checkout is github.com/CrispStrobe/CrispASR at commit 7e2b030780df5c9ad7ede6ac1935bc783b037d18 (2026-10-01, version 0.8.40), with its ggml submodule at 2f5a80d258c46e6ac8eee95f1328c0f58376d7ee.

**Verdict.** The full `crispasr` build fails the China rule, in the same way the Moonshine tree did (VO-13): it compiles in data and model code from China-based teams. A build of the Parakeet backend alone passes. That build compiles five CrispASR source files and the ggml CPU backend, and nothing else. The GGUFs for Parakeet v2 and Phonon-2 are reproducible from the original weights with CrispASR's own converter, as far as could be checked here (see below). So the CrispASR path goes on, but only as this small build.

**The maintainer.** GitHub user CrispStrobe (account made 2023-12-22) shows no name or location on the profile. Its own Flutter app, CrisperWeaver, ends its README with "Copyright © Christian Ströbele · Stuttgart, Germany." (github.com/CrispStrobe/CrisperWeaver). Four CrispASR commits carry the author "Christian Ströbele (Administrator)". That is self-stated. No independent record (a company register, a talk, a paper) was found, and the web-search budget of this session ran out before more could be tried. Other facts from the git history:

- The repo was made on 2026-03-29. Its root commit is "whisper.cpp fork with Cohere Transcribe Conformer support": the whisper.cpp history was not kept, so the fork point cannot be read from git.

**China-based code paths.** Besides the two data tables, the full build links CrispASR's own C++ ports of many models from China-based developers: Qwen3-ASR and Qwen3-TTS, FireRedASR, FunASR/Paraformer, SenseVoice, CosyVoice 3, GLM-ASR, MiMo, MOSS, IndexTTS and OmniVoice. These are reimplementations, not vendored code, but the one `crispasr-lib` target links all of them. `crispasr-core` also holds `crispasr_cache`, the code that downloads models from Hugging Face. The Parakeet build leaves all of that out. Its binary was checked with `strings` and `nm`: no omnivoice, pinyin, kaldi, qwen or firered symbol or string, no `crispasr_cache`, no curl or http, and `ldd` names only libc and libm.

**The GGUFs.** `cstr/parakeet-tdt-0.6b-v2-GGUF` (revision 8878172f) and `cstr/phonon2-GGUF` (revision 3ed3e6ad) say they were made with `models/convert-parakeet-to-gguf.py` and quantized with `crispasr-quantize`. The converter needs the Python packages gguf, sentencepiece, librosa and zstandard. None is on this box, and PyPI is not on this task's list of allowed downloads, so the converter could not run as it stands. It was run instead with four small stand-ins: a GGUF writer that only records what it is given, a SentencePiece reader that reads the piece list from the tokenizer protobuf, librosa's slaney mel filterbank from transformers' `mel_filter_bank`, and `zstd -dc` for zstandard. All the weight handling (the .nemo and Phonon-2 container readers, the five-value expansion, the name mapping, the F16 and F32 choices) is CrispASR's own code at the commit above. The recorded output was compared with the published F16 files:

- Parakeet v2, from `nvidia/parakeet-tdt-0.6b-v2.nemo` (revision ae9ad070, SHA-256 d99e3995...): all 725 tensors byte for byte the same as `parakeet-tdt-0.6b-v2.gguf`, and all 25 metadata keys the same.
- Phonon-2, from `FermionResearch/Phonon-2` at the revision the card pins (9c7fef35; archive SHA-256 98125795..., the same as at the current head): 724 of 725 tensors byte for byte the same as `phonon2-f16.gguf`. The other is the mel filterbank, which the stand-in computes; it differs by at most 3.7e-9. One metadata key differs: the converter now writes `parakeet.language = en`, added after the GGUF was published.
- `crispasr-quantize`, built from the same commit, made Q8_0 and Q4_K from those F16 files. Parakeet v2 Q8_0 came out byte for byte the published file (SHA-256 9da7c8a5...). The Phonon-2 Q8_0 and Q4_K have the same 725 tensors as the published files; the published ones lack two metadata keys (`general.source.url`, `general.source.sha256`). The Parakeet v2 Q4_K differs in 218 of its 725 tensors (the Q4_K ones); the published file is from 2026-05-20, and `examples/crispasr-quantize` has 65 commits since then, so a changed quantizer is the likely cause; it was not traced further. The bench below uses the Q4_K made here.

What this does not show: that the stand-ins match the real packages in every case (only the filterbank depends on one, and it is within float rounding), or that the C++ runtime is free of faults. The README of CrispASR says nothing about security review.

## Caveats

Coverage is uneven. Only Groups A (part) and B (Phonon-2 only) produced surviving claims. All of Group C, all of Group D, and the Grok, Meta Muse and Gemini items have no verified evidence. Read their absence as 'could not verify', not as a finding. Six claims were refuted, among them Voxtral's latency/accuracy trade-off numbers and NVIDIA's own deployment framing for Canary-Qwen, so no latency numbers for those models are confirmed. Every RTFx figure is batched A100 GPU throughput. None measures single-stream CPU latency on this box (desktop CPU, GTX 1060) or on a phone, which is the metric the voice bridge needs. The leaderboard snapshot is from March 2026 and may be out of date. Phonon-2 is days old (weights 2026-09-28, repo 2026-08-28). Its speed numbers are vendor-only. Its leaderboard PR is unmerged. Its runtime is Python/MLX, and the Python-free path depends on third-party GGUF/ONNX ports that nobody has tested. CrispASR has a single maintainer whose location is unknown, and its support list is self-reported and has not been built here. Two license questions are open: Phonon-2's retraining used SPGISpeech under Kensho's restrictive terms, and CC-BY-4.0 requires attribution in any app that ships the weights. The Detta privacy findings come from the vendor's own policy, and no network-traffic audit exists. Whether 'Qwen inside' counts as China-based provenance (Canary-Qwen, Phonon-1) is a policy call for the owner, not a sourced fact.

## Open questions

- Do 'Grok voice transcribe 2.0', 'Meta Muse voice transcribe' and Gemini transcribe/TTS exist as named? What are their terms, and what are the retention and training-on-audio defaults for every Group C cloud provider? This needs a dedicated search pass.
- Where is the CrispASR maintainer (CrispStrobe / cstr) based? Do the cstr Parakeet and Phonon-2 GGUFs actually run on this box's CPU and on Android, and what single-stream latency do they give?
- Does Kyutai stt-1b-en_fr run in real time on a desktop CPU or the GTX 1060 through the Rust stt-rs binary, and is there any Android path besides MLX on iOS?
- Does Handy's Parakeet path use sherpa-onnx (excluded) or transcribe-rs/ONNX Runtime, and what are the licenses and provenance of onnx-asr and parakeet-rs as alternatives to CrispASR?
