# Cursor (IDE agent) — Cursor 3.x as of 2026-08 (forum posts cite 3.17.19 on 2026-08-25; Cursor 3.0 shipped 2026-04-02)


## interactionModel
Two surfaces. (1) The classic IDE (VS Code fork) with an Agent chat panel, Agent Tabs (side-by-side or grid, since 3.0), a live diff view while the agent edits, and a bottom review bar (Keep All / Reject All, Next/Previous File); /agent-review runs a Quick or Deep review pass. (2) The Agents Window (Cmd+Shift+P -> Open Agents Window; Open IDE to return), an agent-first surface built from scratch for Cursor 3.0: a sidebar lists every agent (local, git-worktree, cloud, remote SSH, and ones started from iOS/web/Slack/GitHub/Linear), a central prompt, and a right-side inspection panel (files, sandboxed terminal, browser, review pane that stages/commits/opens PRs). Official docs do not describe per-agent status badges or an inbox; the iOS app documents push notifications when an agent 'finishes, needs input, or is ready for review'.

Prompt surface: modes Agent / Plan / Ask, rotated with Shift+Tab. Plan mode: agent asks clarifying questions, researches the codebase, writes a Markdown plan you edit inline, then you click build; plans save to the home directory by default, 'Save to workspace' moves them to .cursor/plans/. Slash commands drive most orchestration: /worktree, /best-of-n model1,model2 task, /apply-worktree, /delete-worktree, /in-cloud, /babysit, /side, /btw, /fork, /summarize, /goal, /loop, /automate, /create-rule. Messages typed while the agent runs are queued (Enter) or sent immediately (Cmd+Enter); since 2026-08-19 a steering message waits for the next tool call instead of interrupting mid-action. Any skill can be pinned as a Custom Mode with Option/Alt+Enter and shows a badge in the input.

Approval/gating UX: Run Modes (3.6, 2026-05-29) for Shell, MCP and Fetch calls. Auto-review (default): allowlisted calls run at once, sandboxable commands run in the sandbox, everything else goes to a classifier subagent (Claude 4.5 Haiku or GPT-5.4 Mini) that allows, asks the agent to try another approach, or shows you an approval prompt; you can give the classifier custom instructions. Allowlist mode and Run Everything are the alternatives. Rules live in ~/.cursor/permissions.json and sandbox.json (project-level too). Docs call this 'best-effort guardrails rather than a hard security boundary'. MCP tools ask for approval by default; enterprise admins can enforce tool allowlists. Hooks (beforeShellExecution, beforeMCPExecution, beforeReadFile, ...) can return permission allow|deny|ask with a user_message and a separate agent_message.

Cloud agents: launched from the desktop dropdown, cursor.com/agents, iOS/iPad, Slack, GitHub/Bitbucket comments, Linear, or the API. You watch the run transcript, can take over the agent's remote desktop and hand it back, and get screenshots/videos/logs as PR artifacts. Subscriptions (2026-08-19, cloud only) let an agent end its turn and wake when a PR/CI/Slack/timer event lands as a follow-up in the same conversation. /goal gives a long-lived objective (Ctrl+C pauses it in the CLI). Conversation search (3.11, 2026-07-10) indexes thousands of transcripts locally; Cmd+F searches inside one.


## caching
Prefix stability is not documented anywhere; Cursor never describes system-prompt/tool-list ordering, cache breakpoints, or cross-agent prefix sharing. What is documented: (1) Self-summarization (blog 2026-03-17): Composer is trained to compact its own context at a fixed token trigger into ~1,000-token summaries; Cursor states this 'reduces the error from compaction by 50% ... while using one-fifth of the tokens and reusing the KV cache'. (2) Dynamic context discovery (blog 2026-01-06): long tool outputs are written to files and read with tail/grep; terminal sessions are synced to files; the full chat history is written to a file before summarization so the agent can grep what the summary lost; MCP tool descriptions are synced to a folder and only tool names stay in static context (46.9% fewer agent tokens on runs that call MCP tools); skills expose only name+description statically and load bodies on demand; large files are condensed to signatures. (3) Per-step re-send is avoided by keeping a single conversation and pruning/summarizing (auto when full, or /summarize); forking from an earlier message truncates context so the fork does not carry the parent's tail. (4) Subagents have their own context windows; docs warn 'five subagents in parallel uses roughly five times the tokens'. (5) Router (Teams/Enterprise, blog 2026-08-06) picks a model per request; Cursor says its live-traffic cost data 'captures ... cache misses caused by switching models', but no stickiness policy is documented. (6) Cache economics are exposed, not engineered for you: per-model cache-read/cache-write prices in the pricing table; the Cloud Agents API GET /v1/agents/{id}/usage returns inputTokens, outputTokens, cacheWriteTokens, cacheReadTokens per run; the SDK emits per-turn usage events. Orchestration overhead complaints: worktree setup runs as chat messages and 'burns unnecessary tokens' (forum, 2026-04); /apply-worktree costs more tokens; skills are not copied to cloud or SSH agents.

Subagents: Markdown+frontmatter in .cursor/agents (or .claude/agents, .codex/agents, ~/.cursor/agents) with name, description, model (inherit or e.g. composer-2.5[fast=false], claude-opus-5[effort=high], [context=300k]), readonly, is_background; built-ins Explore, Bash, Browser; foreground blocks, background returns at once; each run gets an agent id you can resume; an Await tool waits on background shells/subagents. Hooks: hooks.json at enterprise/team/project (.cursor/hooks.json)/user (~/.cursor/hooks.json) with precedence in that order; events sessionStart/End, preToolUse/postToolUse/postToolUseFailure, subagentStart/Stop, beforeShellExecution/afterShellExecution, beforeMCPExecution/afterMCPExecution, beforeReadFile, afterFileEdit, beforeSubmitPrompt, preCompact, stop, afterAgentResponse, afterAgentThought, Tab hooks, workspaceOpen; command hooks (JSON stdin/stdout, exit 2 = deny) or prompt hooks (LLM evaluates a condition); options timeout, matcher, loop_limit (default 5), failClosed (default false); cloud agents run command hooks only and skip MCP hooks. MCP: .cursor/mcp.json or ~/.cursor/mcp.json; stdio, SSE, streamable HTTP; OAuth with static client credentials; ${env:NAME}, ${workspaceFolder} interpolation; approval by default; enterprise tool allowlists; one-click installs from the Marketplace. Plugins: two formats, Agent Plugins (plugin.json; skills + MCP servers) and Cursor Plugins (.cursor-plugin/plugin.json adding rules, agents, commands, hooks, variables); multi-plugin repos via .cursor-plugin/marketplace.json; public Marketplace (30+ plugins) and private team marketplaces. Commands: .cursor/commands slash commands (since 1.6). Automations: triggers from cron, GitHub/GitLab/Bitbucket PR events, Slack, Linear, webhook, Sentry, PagerDuty, defined in the Agents Window, cursor.com/automations, or /automate. Programmatic: CLI (agent, -p/--print, --output-format text|json|stream-json with typed system/user/assistant/tool_call/result events and session_id, --worktree, & to hand a conversation to the cloud, --force/--yolo), @cursor/sdk for Node 22.13+ (launch, stream, resume, follow-up, cancel, usage events), Cloud Agents REST API v1 (agents, runs, SSE stream, cancel, usage, artifacts; no webhooks in v1), and self-hosted workers (agent worker start; Helm chart/K8s operator) that keep code and tool execution on your infra while Cursor's cloud does inference and planning.


## multiAgent
Parallelism primitives: Agent Tabs (grid of chats in the IDE); /worktree gives one agent its own git worktree (setup via .cursor/worktrees.json setup-worktree[-unix|-windows] commands or script, $ROOT_WORKTREE_PATH for copying files; cap cursor.worktreeMaxCount default 25 per machine, periodic cleanup); /best-of-n sonnet,gpt,composer <task> runs the same task per model in separate worktrees and shows results side by side, suggesting a winner, but 'compares runs only. It does not merge changes back'; /apply-worktree and /delete-worktree; the Agents Window lists all local, worktree, cloud, and SSH agents and can move an agent local <-> cloud. Cloud: unlimited parallel isolated VMs with builds (3x faster start, 2026-08-13), computer use with a desktop and browser, /in-cloud spawns a cloud subagent for the next task, /babysit hands a PR to a cloud subagent that iterates until mergeable (3.7, 2026-06-17), subagents on isolated cloud machines with clean context (2026-08-19), long-running agents (examples of 25-52 hour runs, a 151k-line PR) that propose a plan and wait for approval first, subscriptions that let an agent sleep until a PR/CI/Slack/timer event, /goal for objectives, automations for event-driven fleets, and Cursor claims 35% of its own merged PRs come from cloud agents. Supervision across many agents: the sidebar plus push notifications (finishes / needs input / ready for review) on iOS with lock-screen Live Activities; a shareable run URL lets teammates read a run (read-only unless admins enable follow-ups); the API exposes agent status ACTIVE|IDLE|ARCHIVED and run status CREATING|RUNNING|FINISHED|ERROR|CANCELLED|EXPIRED with an SSE event stream and per-run token usage. Token overhead: subagents multiply tokens roughly N-fold; there is no documented shared-prefix or shared-context mechanism between parallel agents; the Router can lower blended cost per request (claimed 41-68% below a single frontier model) only on Teams/Enterprise. Community reports: HN users citing $2k/week before switching tools, a Cursor 3 thread reporting $2,000 in two days of cloud agents, and forum users unable to get /worktree to work in more than 20 attempts (2026-04).


## forkTimeTravel
- supported: partial. Rewind = restore a file checkpoint (messages stay); branch = Fork Chat (copies messages up to a point into a new flat conversation) or a Side Chat (hidden-context parallel thread). There is no tree view, no parent-pointer navigation, no replay, and no merge of forks.
- ux: Checkpoints: created automatically 'before making significant changes'; click a checkpoint in the chat timeline to preview files at that point, then Restore; also a 'Restore Checkpoint' button on previous requests or the + on hover. 'Restoring a checkpoint reverts files only; it does not remove messages from the conversation.' Stored locally, separate from Git; docs say use Git for permanent history. A regression thread (3.12.30, 2026-08-02) shows the Restore control sometimes not rendering; staff workaround is VS Code 'Local History: Find Entry to Restore'. Fork: 'Fork Chat' from the tab menu, sidebar, or command palette copies every message and subagent; forking from a specific message (three-dots menu on the message, or /fork) copies the conversation through that message and drops everything after it, including later subagents. In the Agents Window you can only fork from the latest message (right-click in sidebar); in the Editor from any message. Staff (2026-08-18) confirm forking from an earlier message 'releases the tokens accumulated after that point', so the fork's context size equals the fork point; the displayed token count only updates after the next response. A bug where the fork re-answered the previous turn was fixed in 3.14 (after 2026-07-27). Merging a fork back is a declined feature request (2026-04-20; staff suggested exporting transcripts or using subagents). Side chats (3.11): /side, /btw, Shift+Cmd+S, or 'Ask in Side Chat' on a selection; the parent history is copied in as hidden reference context and does not appear in the side-chat transcript; @-mention the side chat from the main thread to pull its result back; no nesting; local only. Docs contradicted each other on what a fork copies until staff clarified on 2026-08-25. CLI: agent ls / agent resume / --resume <id> / --continue; a --fork-session flag is only a feature request; no checkpoint restore command is documented.
- dataModel: Reverse-engineered (secondary sources; Cursor publishes nothing). Conversations live in SQLite: <globalStorage>/state.vscdb, table cursorDiskKV (text key, BLOB value holding UTF-8 JSON). Keys: composerData:<composerId> = conversation header {_v:13, composerId, name, fullConversationHeadersOnly:[{bubbleId, type(1 user|2 assistant), serverBubbleId}], conversationMap (empty in v3), context{fileSelections,...,cursorRules}, unifiedMode agent|chat|plan|edit, modelConfig{modelName,maxMode}, status, createdAt, isAgentic}. bubbleId:<composerId>:<bubbleId> = one message (~60 fields: text, richText, type, toolFormerData/toolResults {name, params, userDecision, result}, tokenCount, checkpointId, allThinkingBlocks, thinkingDurationMs, createdAt). checkpointId:<composerId>:<checkpointId> = workspace snapshot {files:[{uri, originalModelDiffWrtV0:[{original{startLineNumber,endLineNumberExclusive}, modified[lines]}]}], nonExistentFiles, newlyCreatedFolders, activeInlineDiffs}; user bubbles reference it via checkpointId; a missing one yields '[internal] Blob not found'. messageRequestContext:<composerId>:<messageId> = the full request context sent to the model for that turn. composer.content.<hash> = content-addressed large-text blobs shared across conversations. composer.composerHeaders = central index (3.0+), each entry tagged with workspaceIdentifier. agentKv:* = bulk agent state (a 2026-08 report: 30 GB DB, 1.96M rows, 67.6% bubbleId, 29.7% agentKv; staff command 'Developer: GC Agent KV Blobs'). Ordering is by array position in fullConversationHeadersOnly: 'No parent pointers or tree structure'. A fork is therefore a new composerId whose bubble list is a copy of a prefix of the parent's; no parent link is documented. File-level checkpoint artifacts also sit at <globalStorage>/anysphere.cursor-commits/checkpoints/<id>/{files/, diffs/<uuid> (fsPath, fileUuid, diffChanges, gitInfo, kind), metadata.json (agentRequestId, requestFiles, deduplicatedGitInfos, workspaceId, startTrackingDateUnixMilliseconds)}. CLI/SDK agents use a separate 'checkpoint store': ~/.cursor/chats/*/*/store.db with tables meta (agentId, latestRootBlobId, name, mode, createdAt, lastUsedModel) and blobs (one secondary source; semantics of latestRootBlobId unverified). Transcripts: ~/.cursor/projects/*/agent-transcripts/*.jsonl, rows {role, message.content:[{type:text|tool_use, name, input}]} with no timestamps, no usage, no tool_result, no ids (forum, 2026-07); subagent runs go to separate sidechain files; background subagents write progress to ~/.cursor/subagents/.


## steal
- **Rewind restores files, never the transcript. A checkpoint restore reverts the workspace to the snapshot but leaves every message (and every allow/deny) in the conversation.** — For daisugi the gate's verdict log must be append-only evidence. Cursor shows users accept a rewind that does not erase history, so the cockpit can offer 'restore workspace to step N' without ever deleting proof records. [https://cursor.com/docs/agent/chat/checkpoints]
- **Two branch primitives with different context costs: Fork (copy the prefix up to a message; later tokens are released) and Side Chat (parallel thread seeded with hidden parent context, @-mention to pull its result back, no nesting).** — Daisugi's prompt tree needs exactly this split: a true fork node that shares the parent's byte-identical prefix (cache hits continue) versus a cheap consult thread that never enters the main context. Cursor's staff-confirmed rule that a fork's context size equals the fork point is the right accounting model. [https://cursor.com/help/ai-features/side-chats]
- **Steering messages are delivered at the next tool-call boundary instead of interrupting mid-action (Enter twice or send-now to override).** — The gate already sits at the tool-call boundary. An operator note injected at the next gate decision is a natural, non-destructive intervention for many agents at once; no partial edits get torn. [https://cursor.com/changelog/08-19-26]
- **Three-tier run mode: allowlist runs at once, sandboxable actions run sandboxed, only the residue reaches a judge that can allow, ask the agent to try another approach, or escalate to the human; the judge accepts operator instructions.** — Maps directly onto daisugi: proven-in-envelope -> run; provable-in-sandbox -> run sandboxed; unprovable -> deny with a reason the agent can act on, escalate only when the agent insists. The 'try another approach' outcome is the important third state between allow and ask. [https://cursor.com/docs/agent/security/run-modes]
- **Hook contract with two audiences: permission allow|deny|ask plus user_message (for the human) and agent_message (for the model), exit code 2 = deny, and a failClosed switch.** — A gate verdict should carry a human-readable why for the cockpit and a machine-actionable why for the agent. Cursor's schema is a clean wire format daisugi can emit unchanged for Cursor users, with failClosed forced on. [https://cursor.com/docs/agent/hooks]
- **Context as files with a names-only static index: tool outputs, terminal sessions, MCP tool descriptions, and skills live on disk; static context holds names and one-line descriptions; the agent greps/reads bodies on demand (46.9% fewer tokens on MCP runs); the full history is written to a file before compaction.** — The garden should present pathways the same way: a tiny stable index in the prefix (cache-friendly) and full pathway bodies and gate logs as files. This is the documented mechanism behind Cursor's token savings, not a marketing claim. [https://cursor.com/blog/dynamic-context-discovery]
- **Subscriptions: an agent ends its turn, subscribes to an event source (PR/CI/Slack/timer), and wakes with the event delivered as a follow-up in the same conversation; the API exposes per-run inputTokens/outputTokens/cacheWriteTokens/cacheReadTokens.** — A many-agent cockpit needs idle agents to cost zero and 'needs input' to be an event, not a polling state. Reporting cache read/write per run makes cache-hit ratio a first-class per-agent metric for the garden's tokens-saved view. [https://cursor.com/docs/cloud-agent/capabilities]

## avoid
- **Hooks fail open by default: any exit code other than 0 or 2 lets the action proceed, and failClosed defaults to false.** — For a safety gate the default must be deny-on-error. Daisugi should ship fail-closed and treat a crashed verifier as a denial, which is the opposite of Cursor's default. [https://cursor.com/docs/agent/hooks]
- **An LLM classifier as the guardrail. Auto-review's judge 'can allow a call you would have blocked, or block a call you would have allowed'; run modes are 'best-effort guardrails rather than a hard security boundary'.** — This is the exact gap daisugi exists to close: a probabilistic judge cannot give a proof. Do not copy the classifier as the primary decision; use it, if at all, only to suggest envelope edits. [https://cursor.com/docs/agent/security/run-modes]
- **Flat, copy-on-fork conversation storage with unbounded growth: messages are an ordered array with no parent pointers, a fork duplicates the prefix into a new conversation, forks cannot merge, docs contradicted each other about what a fork copies, and one user's state.vscdb reached 30 GB (1.96M rows) with staff admitting compaction 'genuinely can't help you here'.** — Daisugi's tree needs real parent ids and content-addressed shared prefixes so forks are O(1) and the cache prefix is provably identical; otherwise the garden's history becomes both expensive and ambiguous. [https://forum.cursor.com/t/state-vscdb-grows-to-30gb-due-to-bubbleid-agentkv-entries/167641]
- **Orchestration as chat slash commands: /worktree runs setup scripts as chat turns that 'burn unnecessary tokens', pollute the transcript, are not reliably honored (>20 failed attempts reported), and leave no visual indicator of which agent is in which worktree.** — Agent placement, isolation, and budget must be deterministic cockpit actions executed by the harness, not prompts the model may or may not follow, and never billed as model tokens. [https://forum.cursor.com/t/cursor-3-worktrees-best-of-n/156507]
- **An agent-first cockpit that hides both the code and the bill: users report they 'can only sit at one granularity level', no per-request cost is shown in the editor (dashboard only), the context-usage indicator was removed in 2.0, cloud VM pricing is undisclosed, and HN users cite $2k/week bills.** — Daisugi's operator surface must let the operator zoom from fleet to a single proposed action and back, and show the per-step budget and cache-hit state inline, or the supervision cockpit becomes the thing people leave for a cheaper CLI. [https://news.ycombinator.com/item?id=47618084]

## loadBearingClaims
- Cursor checkpoints are automatic local file snapshots; restoring one 'reverts files only; it does not remove messages from the conversation', and they are stored separately from Git. [https://cursor.com/docs/agent/chat/checkpoints]
- Fork Chat from the tab/sidebar copies every message and subagent; forking from a specific message copies the conversation through that message and drops everything after it; a Side Chat seeds the model with the parent history as hidden context and 'is a parallel thread, not a fork'; nesting is not supported. [https://cursor.com/help/ai-features/side-chats]
- Cursor hooks return permission allow|deny|ask with separate user_message and agent_message; exit code 2 blocks; other non-zero exit codes fail open unless failClosed (default false) is set. [https://cursor.com/docs/agent/hooks]
- Cursor's conversation store (reverse-engineered, not official) is a linear array: composerData.fullConversationHeadersOnly orders bubbles by position with 'No parent pointers or tree structure'; checkpoints are keyed checkpointId:<composerId>:<checkpointId> and referenced from user bubbles. [https://github.com/Callum-Ward/cursaves/blob/main/docs/how-cursor-stores-chats.md]
