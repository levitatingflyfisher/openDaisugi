# Cline (VS Code / JetBrains extension, CLI TUI, Kanban board, @cline/sdk). Latest: extension v4.1.16 (2026-08-26), CLI cli-v3.0.60 (2026-08-26), SDK announced 2026-05-13 (Apache-2.0); VS Code extension has run on the SDK session layer since v4.0.0 (2026-06-26). ~67k GitHub stars.


## interactionModel
Sidebar chat in the IDE (or the CLI TUI). Two modes: Plan (read/search/discuss, no edits or state-changing commands; enforced by prompt plus a plan-mode command-guard hook that rejects file-editing run_commands calls) and Act. Toggle: Cmd/Ctrl+Shift+A in VS Code, Tab in the CLI TUI; optional separate model per mode; conversation carries over. Every user message is wrapped as <user_input mode="act|plan|yolo"> so the model can see mode switches in the transcript. Gating: each tool call is evaluated against per-category Auto Approve toggles (read project files / read all files / edit project / edit all / execute safe commands / execute all commands / use browser / use MCP servers); commands carry a per-call, model-supplied requires_approval flag; 'YOLO mode' auto-approves everything including Plan->Act transitions. The 'max N API requests before pausing' cap and the master auto-approve toggle were REMOVED in v3.35 (2025-10-31). CLI: --auto-approve <bool> defaults to true; Shift+Tab toggles auto-approve-all; status bar shows model, context usage, cost, workspace/branch, git diff stats, Plan/Act, auto-approve state. SDK hosts get a requestToolApproval({toolName,input}) callback answering {approved:boolean}; a denial 'counts as a response' and the agent proceeds. Per-step visibility: task header shows a context-window progress bar (input/output tokens vs model max), running cost updated after each API request (token detail moved into a hover tooltip in v3.31, 2025-09-25), a manual compact button, and a 'Task Timeline' storyboard (v3.15, 2025-05-10): one block per tool call / message / edit, hover for summary and timestamp. Subagents show per-subagent tool calls, tokens and cost in chat. Kanban (2026-03-26, npx kanban, localhost:3484): Backlog / In Progress / Review / Trash columns, one ephemeral git worktree + terminal per card, card shows the agent's latest message or tool call, cards blocked on approval land in Review, click a diff line to leave a comment that is routed back to the agent, linked cards auto-start when their predecessor is trashed; runs Cline CLI, Claude Code, Codex, OpenCode. Edit-and-regenerate a previous message offers 'Reset Chat' / 'Reset Code'.


## caching
Full conversation is re-sent every step (standard agent loop); savings come from provider prefix caching plus context trimming. Anthropic-compatible route (source, sdk/packages/llms): cache_control {type:'ephemeral'} is applied to the LAST text part of the LAST user message (loop from the end in ai-sdk.ts) and an ephemeral cache option is set at request level; Bedrock gets a cachePoint on the last user message (fixed in 4.1.4 after reporting zero cache reads); Qwen/OpenRouter get an OpenAI-compatible cache_control shape. Prefix stability: system prompt contains {{CURRENT_DATE}} = new Date().toLocaleDateString() (changes daily, not per turn); user messages are wrapped in <user_input mode=...> with no timestamp. Context trimming that is cache-aware: duplicate file reads replaced with a [DUPLICATE FILE READ] notice; 4.0.0 'batching outdated-read rewrites to preserve provider prefix caches'; older docs: maxAllowedSize = max(contextWindow - 40_000, contextWindow * 0.8), paired message removal keeping the first message, and 'aggressively truncating older messages can break the cache' as the stated reason for conservatism; OpenRouter middle-out transform deliberately not applied to Claude because it would break the cache. Auto Compact summarises near the limit (model-dependent, else rule-based truncation); 4.1.7 compacts and retries once on context overflow. Third-party audit (2026-05-27) rates Anthropic caching 'partial' (breakpoint sits on the volatile current turn rather than stable content) and OpenAI-native 'silently broken' (no prompt_cache_key). Claude Code provider spawns a fresh CLI process per message with dynamic headers, so supportsPromptCache:false and no cache hits (Discussion #9892, 2026-03-19). Cache read/write tokens are shown in the task header and history (with provider gaps, e.g. Vertex #4788). Multi-agent: subagents get their own context window; subagent cost is tracked per subagent and rolled into task total (aggregatedAgentsCost / aggregateUsage in metadata). Static MCP docs were moved out of the system prompt into a load_mcp_documentation tool (~8k tokens on demand). Not documented: any cache breakpoint on the system prompt or tool definitions in v4.

## multiAgent
Subagents (v3.58.0, 2026-02-12; experimental, on by default): use_subagents tool spawns parallel read-only researchers (read_file, list_files, search_files, list_code_definition_names, read-only execute_command, use_skill; no edits, browser, MCP or nesting); each has its own prompt, context window and token budget and returns a report focused on file paths; launch is gated by the 'Read project files' auto-approve setting; per-subagent tool calls / tokens / cost shown in chat and rolled into the task total. Sub-session ids are <rootSessionId>__<agentId>; SessionLineage records parentSessionId, agentId, parentAgentId, conversationId, isSubagent. Agent Teams (CLI, SDK, Kanban only; not in the IDE): `--team-name <name>` (hidden flag) or /team; one coordinator with team_spawn_teammate, team_delegate_task, team_check_status, team_get_result; state in ~/.cline/data/teams/<name>/ (task-board.json, mailbox.json, mission-log.json) persists across sessions; --no-teams to disable; docs warn 'a single agent with good tools is usually more efficient than a team'. Kanban runs many CLI agents (mixed runtimes) in parallel worktrees, 'monitor hundreds of agents at a glance' via each card's latest message/tool call, dependency chains, auto-commit/auto-PR. Observability: OpenTelemetry events task.tool_used{tool_name,success,duration_ms,auto_approved}, task.tokens{tokens_in,tokens_out,cached_tokens,cost}, task.checkpoint_used{action: create|restore|compare}, task.mode{previous_mode,new_mode}, task.subagent_started/completed. No published numbers on orchestration token overhead.


## forkTimeTravel
- supported: partial: rewind-by-checkpoint and edit-to-regenerate exist; no tree view, no named branches, no replay, no navigation between siblings. A message-restore silently creates a new session and leaves the old one in history, so a tree exists on disk in effect but is not linked or navigable.
- ux: VS Code: a 'Checkpoint' bookmark appears on each user turn that started a run, with Compare (multi-file diff of checkpoint vs current worktree, untracked files included) and Restore. Restore offers three choices: 'Restore Files' (rewind workspace, keep chat), 'Restore Task Only' (delete later messages, keep files), 'Restore Files & Task'. Editing an earlier message rewinds to it with Reset Chat / Reset Code options and pre-fills the text for re-send. CLI TUI: /undo opens a 'Restore to Checkpoint' picker (up/down or Ctrl+P/N, Enter, Esc) listing runs, then a confirm dialog with 'Restore chat only' (rewind conversation, keep current files) or 'Restore chat and workspace' (warns: runs git reset --hard and git clean -fd). Kanban: per-card diff can be scoped to message ranges. Restore into a run that auto-compaction folded into a summary fails with 'Run N is folded into a compacted message'. Checkpoints enabled by default; toggle under Feature Settings; only when cwd is a git repo (picked up if git init happens mid-session).
- dataModel: Current SDK/v4 implementation (verified in source; the docs page still describes the older design): NO separate shadow repo. On each user 'run' (the Nth user message that starts an agent turn; tool results do not count) the runtime makes a stash-shaped snapshot inside the user's own repo: `git stash create` plus a synthesized third parent commit holding untracked (non-ignored) files, joined by `commit-tree` with parents [HEAD, index, untracked], message 'cline checkpoint session=<sessionId> run=<n>'. The SHA is pinned under a private ref refs/cline/checkpoints/<sessionId>/<runCount> (GC-safe, invisible to `git stash list`). If the tree is clean it falls back to kind:'commit' = HEAD. Entries {ref, createdAt(ms), runCount, kind:'stash'|'commit'} are stored in session metadata as checkpoint:{latest, history[]}. Restore = git reset --hard <base> ; git clean -fd only if the snapshot has the ^3 untracked parent ; git stash apply <ref>, wrapped in a transaction that first stashes the live worktree under refs/cline/restore-transactions/<uuid> for rollback. Message restore = start a NEW session with initialMessages sliced to the run (optionally omitting the checkpoint message) and checkpoint history filtered to runCount <= N re-pinned under the new session id; the source session is not deleted and no parentSessionId link is written (parentSessionId/agentId/conversationId/isSubagent exist in SessionLineage but are used for subagents). Sessions live under ~/.cline/data/sessions/ (sessions.index.json of SessionRow; manifest schema v1 with messages_path and compaction_path; SQLite store variant). Legacy v3.x (docs): branch-per-task shadow git under VS Code globalStorage, commit after every tool use, nested .git renamed to .git_disabled during snapshots.


## steal
- **Split rewind into three independent restores: files only, conversation only, or both (VS Code), and 'chat only' vs 'chat and workspace' with an explicit warning of the git commands about to run (CLI).** — daisugi's operator will often want to keep the envelope/conversation but undo the agent's edits, or vice versa; naming the two axes separately avoids the destructive 'restore everything' default. [https://docs.cline.bot/core-workflows/checkpoints]
- **Snapshots as private refs in the user's own repo: stash-shaped commit with a synthesized third parent for untracked files, pinned at refs/cline/checkpoints/<session>/<run>, restore wrapped in a rollback transaction ref.** — No shadow repo to corrupt, GC-safe, invisible to git stash list, and untracked agent-created files round-trip; the transaction ref is a cheap way to make a fail-closed restore. [https://github.com/cline/cline/blob/main/sdk/packages/core/src/hooks/checkpoint-hooks.ts]
- **Task Timeline storyboard: one block per tool call / message / edit in the header, hover for summary and timestamp; Kanban cards show only the agent's latest message or tool call.** — This is the glanceable per-agent strip a many-agent gate cockpit needs; colour it by allow/deny and it becomes the supervision surface. [https://cline.bot/blog/cline-v3-15-unveiling-task-timeline-gemini-implicit-caching-new-community-docs]
- **Hook stdout contract {cancel, contextModification, errorMessage}: a cancelling hook's message travels back to the model as stop+reason; context is injected only when the run continues; PreToolUse runs after the model has decided and before execution, with PreCompact as a separate event.** — Matches daisugi's gate exactly (verdict + reason fed back to the agent) and gives a place to hook compaction so the envelope survives summarisation. [https://cline.bot/blog/cline-v3-36-hooks]
- **Per-tool policy trichotomy in the SDK: {autoApprove:true}, {autoApprove:false}, {enabled:false} where the model does not even see the tool.** — A gate that can hide a tool from the model is cheaper than one that denies it every step; daisugi's envelope can project to this at session start. [https://docs.cline.bot/sdk/guides/permission-handling]
- **Progressive disclosure for skills (~100 tokens of metadata per skill at startup, body only on use_skill) and moving static MCP docs into a load_mcp_documentation tool.** — Garden pathways should not sit in the cached prefix; list them cheaply and load on demand so the prefix stays small and stable. [https://docs.cline.bot/customization/skills]
- **OpenTelemetry event vocabulary: task.tool_used{auto_approved}, task.tokens{cached_tokens,cost}, task.checkpoint_used{action}, task.mode, task.subagent_*.** — A ready-made schema for the cockpit's per-step metrics; add a 'gate verdict' attribute and the garden view falls out of the same stream. [https://docs.cline.bot/enterprise-solutions/monitoring/opentelemetry-events]

## avoid
- **Docs describe one data model (shadow git repo, commit after every tool use) while v4 code does another (stash-commits per user run in the user's repo).** — Operators cannot reason about what a restore will do to their working tree; keep the checkpoint doc generated from, or tested against, the implementation. [https://docs.cline.bot/core-workflows/checkpoints]
- **Legacy shadow-git snapshotting renamed nested .git to .git_disabled and left repos broken on crash/cancel (#4385 plus five linked issues); per-tool-use commits needed a 7s warning / 15s timeout on large repos.** — Never mutate the user's VCS metadata to take a snapshot, and do not snapshot on every tool call in big trees. [https://github.com/cline/cline/issues/4385]
- **Message restore silently starts a new session with no parent pointer; history fills with same-titled sessions and there is no tree UI; earlier bug: a checkpoint could not be restored twice (#8866).** — If daisugi forks, write the parent link and show the tree; an implicit fork with no navigation is worse than an explicit one. [https://github.com/cline/cline/blob/main/sdk/packages/core/src/runtime/host/local-runtime-host.ts]
- **Cache breakpoint placed on the volatile last user message (audit: 'volatile-message bug'), OpenAI-native requests without prompt_cache_key, and the Claude Code provider spawning a fresh CLI per message so caching never hits.** — Put breakpoints on the stable prefix (system + tools + older turns) and keep one process/session; otherwise every step pays full input price. [https://github.com/OnlyTerp/prompt-cache-skills]
- **Removed the 'max N API requests before pausing' budget cap and the master auto-approve toggle in v3.35 as 'complexity without value', after users had depended on them (#3480, #4907, discussion #1375); YOLO also auto-approves Plan->Act.** — A per-step / per-task budget knob is the core of a supervision cockpit; do not fold it into an all-or-nothing switch. [https://cline.bot/blog/cline-v3-35]

Date: {{CURRENT_DATE}}`), near the top, so a date change invalidates the whole cached prefix. The date is evaluated when the host builds the prompt, not per request: the extension builds it once per session build (apps/vscode/src/sdk/cline-session-factory.ts) and the CLI at session start (connectors/session-runtime.ts) and on every Plan/Act switch (interactive/mode.ts), so the prompt is stable across midnight inside a session but changes on every rebuild. Other prefix invalidators exist independent of the date: mode switches swap in/out the plan-mode section (cline.ts: 'a mid-conversation mode switch is an invisible system-prompt swap'), the extension rebuilds sessions on provider/mcpTools/terminalExecutionMode changes (sdk-session-rebuild-scheduler.ts), rules text changes, and for the Cline provider `{{CLINE_METADATA}}` embeds `latestGitCommitHash` and `latestGitBranchName` (workspace-manifest.ts generateWorkspaceInfo -> processWorkspaceInfo; cline-session-factory.ts comment: 'so Cline API observability can extract git remotes and the latest commit hash from the system message'), so any new commit before a (re)build changes the prefix. → corrected: On routes whose provider metadata declares anthropic-cache-control prompt caching (Anthropic-compatible models, plus Qwen models that advertise prompt-cache), the SDK places a single ephemeral cache_control on the last text part of the last user message and nowhere else (Bedrock uses a Converse cachePoint instead). The system prompt (built by buildClineSystemPrompt in @cline/shared, not in ai-sdk.ts) embeds the date via toLocaleDateString() near its top, but the date is stamped when the host builds the prompt (session start, session rebuild, Plan/Act switch), not per request; the cached prefix therefore changes on every prompt rebuild, mode switch, provider/MCP/rules change, and, for the Cline provider, on every new git commit (the prompt embeds the HEAD hash and branch), with the daily date roll being only one of the invalidators.
