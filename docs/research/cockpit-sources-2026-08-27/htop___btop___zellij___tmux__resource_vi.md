# htop + btop + zellij + tmux (resource views and multiplexers). State as of 2026-08-27: htop 3.5.3 (2026-08-16), btop v1.4.7 (2026-05-01), zellij v0.45.0 (2026-08-20), tmux 3.7c (2026-08-17; the '3.8' items exist only in master CHANGES and are unreleased).


## interactionModel
Four distinct operator models, all keyboard-first with an on-screen ramp. (1) htop: one live process table plus header meters; the bottom row is a persistent F1-F10 function bar (F1 help, F2 setup, F3 search, F4 filter, F5 tree, F6 sort, F7/F8 nice, F9 kill, F10 quit) with letter equivalents (h, S, slash, backslash, t, < >, ] [, k, q). Tab/Shift-Tab cycles 'screens' (named tabs, each with its own columns/sort/tree state). Space tags a row, c tags a process and its children, U untags, F9 then acts on all tagged rows through a signal menu. 3.5.0 added --no-function-bar and --no-meters for experts and --readonly to disable every mutating action; 3.5.2 added sticky_follow and a 'stable tree view'. (2) btop: four boxes (cpu/mem/net/proc, plus gpu0-5) with braille/block/tty graphs, full mouse (clickable buttons, scroll, drag scrollbar), Esc/m 'game inspired' menu, F2/o options, F1/h help, keys 1-5 toggle boxes, p / Shift-p cycle up to 9 layout presets, e tree view, E collapse/expand all, Space expands a node, F follows the selected process, u pauses the list, f or slash filters (leading ! = regex), Enter opens a detail box for one process, t/k/s/N terminate/kill/signal/renice, +/- change update_ms in 100 ms steps. The config file is rewritten from in-app changes. (3) zellij: modal. Modes: normal, locked, resize, pane, move, tab, scroll, search, entersearch, renametab, renamepane, session, tmux. The default status-bar plugin draws line 1 as mode ribbons (each mode name with its key, current mode highlighted, LOCKED indicator, session name) and line 2 as hints for the current mode derived from the live keymap (action_key() over ModeInfo keybinds; 'Ctrl + <a|b|c>' grouping), or contextual hints (nested-session descended/ascended, text copied, floating panes visible) plus a 'Tip:'. Two presets: default (Ctrl p then n = new pane) and 'unlock-first' (Ctrl g unlocks, then mode key, then action) to avoid colliding with terminal apps; default_mode can be 'locked'. The compact-bar plugin hides hints until a configured tooltip key (e.g. tooltip "F1") shows them. Built-in UI is all plugins reached via Ctrl o: w session-manager (Tab toggles the EXITED section, Enter resurrects), l layout-manager (open favourite layouts, apply a layout to the current tab keeping or dropping non-matching panes, 'record' a layout from the current tab), p plugin-manager, a about (release notes + tips), s share (web tokens), f zoom into a nested session, ] / [ ascend/descend a nested session (nested_session_handling ask/fullscreen/descend/never). Alt p or Alt+click marks several panes for bulk actions (stack, break to tab, float/embed, close). Since 0.45 pane frames are off by default (pane_frame_style "titles"); stacks render as a list of one-line titles (stacked_pane_list). Gating UX: a resurrected command pane shows a 'Press ENTER to run...' banner instead of running; zellij run --start-suspended does the same on demand; a command pane shows the exit code and offers ENTER to re-run, Ctrl-c to close; plugins requesting a PermissionType get a one-time approval prompt; read-only tokens and zellij watch <session> give view-only access. (4) tmux: prefix key model (C-b then key), C-b : command prompt, C-b ? / list-keys -N for discovery, C-b s / C-b w enter choose-tree (tree of sessions > windows > panes with previews; t tags an item, C-t tags all, ':' runs a command for each tagged item, x/X kill selected/tagged, f filters by a format, O/r sort, v toggles preview, C-h/F1 help), C-b C customize-mode (browse/edit options and key bindings in a list), display-menu and display-popup (-E close on exit, -w/-h size incl. %, -x/-y position, -b border chars, -T title, C-c closes), and in 3.7 non-modal floating panes via new-pane bound to * (currently move/resize by mouse only). Control mode (-C / -CC) turns tmux into a protocol for GUI front-ends (iTerm2, WezTerm, Ghostty).


## caching
Not applicable in the LLM sense: none of these tools hold a model context. The concrete mechanisms that play the same role (do not resend what the client already has) are: tmux control mode streams only deltas per pane as '%output %pane data' (or '%extended-output' with a lag value), wraps every command reply in '%begin ... %end/%error' guard lines, lets the client throttle with 'refresh-client -f pause-after=N' (then '%pause' / 'refresh-client -A %0:continue'), and 'refresh-client -B name:what:format' reports a changed format value at most once per second instead of the client polling; zellij's 'zellij subscribe --format json' emits NDJSON pane_update events with a viewport array and sends scrollback only on the first delivery (is_initial: true, scrollback null afterwards) and emits pane_closed; zellij's plugin API keeps the frequently fired ModeUpdate event small by delivering the keymap once through InitialKeybinds ('their ModeUpdate events arrive with an empty keybinds field from then on - this keeps the frequently fired ModeUpdate lightweight'); the PaneRenderReport event delivers rendered pane text periodically only for panes a plugin subscribed to (permission ReadPaneContents); session state is re-serialised every 1 s (serialization_interval) rather than on every change; btop samples on update_ms (recommended 2000+ ms) with background_update. Nothing about stable prefixes or token reuse is documented because there are no tokens.


## extensions
zellij: WebAssembly/WASI plugins ('Rust is the only language officially supported', community efforts for others); runtime moved from wasmtime to wasmi in 0.44. A plugin is 'a first class citizen in the workspace, just like a terminal pane' with lifecycle load(configuration) -> update(event) -> bool -> render(rows, cols) -> pipe(); optional background workers. It renders by printing ANSI in render() or via a UI-components protocol (table, ribbon, nested_list, text with selection/colour ranges) so themes apply. Events (~45): ModeUpdate, TabUpdate, PaneUpdate, SessionUpdate, Key, Mouse, Timer, RunCommandResult, WebRequestResult, CommandPaneOpened/Exited/ReRun, PaneClosed, UserAction (every action any user performs), PaneRenderReport, ActionComplete, CwdChanged, CommandChanged (foreground argv changed), InitialKeybinds, HintText (contextual hint variants keyed by display width), HighlightClicked, WebServerStatus, BeforeClose. Commands (~100): open_command_pane(_background), rerun_command_pane, run_command, web_request, write/write_chars/write_to_pane_id, send_sigint/sigkill_to_pane_id, new_tabs_with_layout, dump_session_layout, save_layout, override_layout, stack_panes, set_pane_color, rebind_keys, intercept_key_presses, switch_to_input_mode, run_action (any Action, with a context dict returned in ActionComplete), pipe_message_to_plugin, block/unblock_cli_pipe_input, cli_pipe_output. Permissions are declared per capability and approved once by the user: ReadApplicationState, ChangeApplicationState, OpenFiles, OpenTerminalsOrPlugins, RunCommands, WriteToStdin, WriteToClipboard, ReadPaneContents, MessageAndLaunchOtherPlugins, WebAccess, InterceptInput, Reconfigure, ReadSessionEnvironmentVariables, RunActionsAsUser, plus web-server ones. Loading: 'load_plugins' block in config, 'plugin location=' in layouts, keybindings, 'zellij plugin' / 'zellij action launch-or-focus-plugin', the plugin-manager (Ctrl o + p); URL schemes file:, zellij: (built-ins: tab-bar, status-bar, compact-bar, strider/filepicker, session-manager, configuration, plugin-manager, about, welcome-screen, share, multiple-select, layout-manager), http(s):, and bare aliases. Pipes: 'zellij pipe' sends name+payload+args from the CLI; pipes without a destination are broadcast to all plugins; a plugin can apply backpressure on a CLI pipe (UUID pipe-id) and write back to the CLI's stdout. Author's stated policy: 'It is Zellij development policy to create new UI interfaces as built-in plugins'. Layouts and swap layouts are KDL files (layout_dir), dumpable with 'zellij setup --dump-layout default'. tmux: no plugin API; extension is shell scripts run by 'run-shell' (arguments expandable as #{1}, #{2} since 3.7), managed by tpm ('set -g @plugin user/repo', prefix+I install, prefix+U update, cloned to ~/.tmux/plugins/); hooks via 'set-hook' (after-new-window, pane-died, client-attached, session-created ...); formats (#{?cond,a,b}, #{s/a/b/}, loops #{S:} #{W:} #{P:}, variables pane_id, pane_pid, pane_dead, pane_dead_status, pane_current_command) drive status lines, pane-border-format and 'list-* -F' scripting; 'pipe-pane' tees pane output to a shell command; 'capture-pane'; 'wait-for' channels; control mode (-CC) with 'refresh-client -B' subscriptions; display-menu/display-popup for ad-hoc UI; customize-mode for in-app option editing; tmuxp/tmuxinator add YAML session files (session_name, windows, layout, panes, shell_command, start_directory; 'tmuxp freeze'). Unreleased 3.8 master adds set-hook -B / wait-for -E hook subscriptions and new-pane -O modal floating panes. htop: no plugins; a Setup screen (F2) configures meters (columns, modes), screens and colours, persisted to htoprc; dynamic columns/screens come from the PCP variant. btop: themes (~/.config/btop/themes, /usr/share/btop/themes), up to 9 presets, per-box graph_symbol_cpu/mem/net/proc, GPU boxes via optional compiled backends (NVIDIA, ROCm, Intel, Apple IOReport).


## multiAgent
These tools supervise many processes, not agents, but the primitives map directly. zellij: several clients can attach to one session ('multiplayer'); mirror_session false (default) gives each user their own cursor, true mirrors one cursor; since 0.45 each tab is sized to the viewports of the clients viewing it. Read-only observers: 'zellij watch <session>' or a read-only web token; full remote attach over HTTPS with tokens ('zellij attach https://host:8082/session --token ...'). Machine control from outside: '--session <name>' targets any session; 'zellij action list-panes --json' (fields id, is_plugin, is_focused, title, is_floating, tab_id, tab_name, pane_command, pane_cwd, plus -t/-c/-s/-g/-a detail groups), 'list-tabs --json', 'list-clients' (client id, focused pane, running command); most actions accept --pane-id / --tab-id so a supervisor never has to steal focus; 'send-keys --pane-id terminal_3 "Enter" "ctrl c"', write-chars, paste (bracketed) inject input; 'zellij subscribe --pane-id A --pane-id B --format json' fans several panes into one NDJSON stream; 'zellij run --blocking / --block-until-exit-success / --block-until-exit-failure' gives sequencing; new-pane/new-tab return ids; '--layout-string' creates a whole tab of agents from generated KDL; 'zellij pipe' broadcasts a message to every plugin; a plugin can subscribe to UserAction (every action by every client), CommandChanged/CwdChanged per pane, and PaneRenderReport for subscribed panes. Nested sessions (0.45) solve the 'doubled status bar and misdirected keys' problem for zellij-inside-zellij. tmux: many clients per session, session groups (kill-session -g), control mode for programmatic front-ends with per-pane %output and %window-add/%window-close/%session-changed notifications, pipe-pane per pane, wait-for -S/-L channels for synchronisation, run-shell, server-access for user/group permissions, choose-tree tagging plus ':' to run one command over all tagged items. htop: tree view (F5/t) with +/- collapse, tagging (Space, c = process and children) then F9 kill on the set, filter with OR terms separated by '|', screens for alternate column sets, container-name and CCGROUP columns, --highlight-changes for new/old processes. btop: tree with proc_aggregate (children's resources rolled into a collapsed parent), E collapse/expand all, F follow one process, u pause the list, per-process CPU graphs (proc_cpu_graphs), detail box on Enter. Overhead: zellij and tmux are single daemons with per-pane PTYs; zellij has a history of CPU/memory issues (#2911 high CPU 0.39, #1625 memory leak) and a HN report of btop leaking memory; neither is verified for current versions.


## forkTimeTravel
- supported: no (none of the four has a conversation/prompt tree). Nearest: linear snapshot-and-restore of workspace shape (zellij session serialization; tmux-resurrect + continuum) and 'record layout from current tab' (zellij layout-manager). Process state is never captured; commands are replayed.
- ux: zellij: sessions serialize automatically every 1 s (serialization_interval configurable); after exit/crash 'zellij list-sessions' shows them as EXITED, 'zellij attach <name>' recreates layout and commands with each command parked behind a 'Press ENTER to run...' banner (skip with --force-run-commands); in the session-manager (Ctrl o + w) press Tab to show EXITED sessions and Enter to resurrect; 'zellij delete-session' / 'delete-all-sessions' prune; layout-manager (Ctrl o + l) can record the current tab as a named layout and later apply it with OverrideLayout (retain_existing_terminal_panes, retain_existing_plugin_panes, apply_only_to_active_tab); 'zellij action dump-layout' prints the live layout; 'zellij --layout-string <KDL>' spawns tabs from an inline layout. tmux: tmux-resurrect prefix+Ctrl-s saves, prefix+Ctrl-r restores; tmux-continuum autosaves every 15 min (@continuum-save-interval) and can restore on server start (@continuum-restore on); tmuxp 'freeze' exports a running session to YAML and 'load' rebuilds it; native tmux has no snapshots, only 'select-layout <layout-string>' and choose-tree navigation. htop/btop: no time travel; htop screens and btop presets are saved views, not history.
- dataModel: zellij: one KDL layout file per session at ~/.cache/zellij/<version>/session_info/<session>/session-layout.kdl, overwritten every 1 s (single latest snapshot, no history, no parent link); it is the same schema as hand-written layouts (layout > tab > pane with command/args/cwd/plugin/focus/name/borderless/stacked/expanded/floating_panes x y width height/pane_template/tab_template/swap_tiled_layout/swap_floating_layout with min_panes/max_panes/exact_panes) so it can be edited and re-used with zellij --layout; optional pane_viewport_serialization and scrollback_lines_to_serialize (0 = all) add viewport/scrollback text; post_command_discovery_hook customises how the running command is discovered. IDs: panes are terminal_N / plugin_N (bare N = terminal_N), tabs have tab_id, $ZELLIJ_PANE_ID and $ZELLIJ_SESSION_NAME are exported. tmux-resurrect: timestamped text files ~/.tmux/resurrect/tmux_resurrect_YYYYMMDDTHHMMSS.txt (or ~/.local/share/tmux/resurrect) plus a 'last' symlink; tab-separated line types 'pane' (session_name, window_number, window_active, window_flags, pane_index, pane_title, pane_current_path, pane_active, pane_current_command, :full_command), 'window' (session_name, window_index, window_name, window_active, window_flags, window_layout, automatic_rename), 'state' (client_session, client_last_session), 'grouped_session'; pane contents captured with capture-pane -epJ -S into separate archived files and restored by 'cat file; exec shell'. tmux IDs are $N session, @N window, %N pane; window_layout is a checksum + cell tree string (e.g. bb62,159x48,0,0{79x48,0,0,79x48,80,0}) re-applied with select-layout. Programs are restored by re-running the saved command (send-keys), only for names in @resurrect-processes (default 'vi vim nvim emacs man less more tail top htop irssi weechat mutt'); shell env/aliases/history are not restored. htop: ~/.config/htop/htoprc is overwritten on clean exit; multiple screens are stored as 'screen:<Name>=<COLUMNS>' followed by '.sort_key=', '.tree_sort_key=', '.tree_view=', '.tree_view_always_by_pid=', '.sort_direction=', '.all_branches_collapsed=' (Settings.c). btop: ~/.config/btop/btop.conf with presets (max 9; preset 0 = all boxes) and shown_boxes.


## steal
- **A persistent mode ribbon plus a per-mode hint line generated from the live keymap, with an expert escape hatch (compact bar + tooltip key). zellij's status-bar renders mode ribbons on line 1 and, on line 2, hints computed from ModeInfo keybinds (so rebinding updates the hints), or a contextual hint (nested session, floating panes visible, text copied) plus a 'Tip:'. Experts switch to compact-bar with 'tooltip "F1"' so hints appear only on demand.** — daisugi's cockpit has real modes (supervise / prompt / tree / garden). Hints derived from the actual bindings never go stale, and the tooltip toggle is the documented cure for the 'chrome eats my screen' complaint. This is the single most cited reason people choose zellij over tmux ('I don't have to memorize keystrokes'). [https://raw.githubusercontent.com/zellij-org/zellij/main/default-plugins/status-bar/src/main.rs and https://zellij.dev/documentation/faq.html]
- **'Proposed but not yet run' as a first-class pane state: resurrected commands sit behind a 'Press ENTER to run...' banner; 'zellij run --start-suspended' and the layout attribute start_suspended do the same on demand; a finished command pane shows its exit code with ENTER to re-run and Ctrl-c to close.** — This is exactly the gate's allow/deny moment rendered as UI. A gated agent action can be shown as a suspended command pane with the verifier's verdict and reason where zellij shows the banner; approving = ENTER, denying = Ctrl-c. Operators already understand the idiom. [https://zellij.dev/documentation/session-resurrection.html]
- **Stacked panes as a list of one-line titles (stacked_pane_list) with the expanded pane at the bottom, plus swap layouts with min_panes/max_panes/exact_panes constraints that re-tile automatically as panes come and go (Alt+[ ] to cycle).** — Many gated agents need N-to-1 focus: keep every agent visible as a one-line title (status, budget, last verdict) while one is expanded; the constraint-driven swap layouts give the cockpit a declarative rule for 1, 4, 12 agents instead of hand layout code. [https://zellij.dev/documentation/swap-layouts.html and https://zellij.dev/news/nested-sessions-kitty-graphics-new-ui/]
- **A machine-facing control plane beside the human UI: 'list-panes --json' with stable ids (terminal_N / plugin_N), --pane-id targeting on every action so supervisors never steal focus, 'send-keys --pane-id', 'zellij subscribe --format json' NDJSON (pane_update with viewport[] and is_initial, pane_closed), 'zellij run --block-until-exit-success', and '--layout-string' for generated layouts.** — daisugi's gate and garden already run out-of-process; the cockpit should be a client of the same JSON stream the gate emits (proposal, verdict, reason, budget) rather than a special path. zellij shows the shape: ids, idempotent targeting, one NDJSON firehose, blocking flags for sequencing. [https://zellij.dev/documentation/programmatic-control.html and https://zellij.dev/documentation/zellij-subscribe.html]
- **Tree mode with tagging and bulk verbs: tmux choose-tree (prefix s / w) shows sessions > windows > panes with previews, t tags, C-t tags all, f filters by a format expression, O/r sort, x/X kill selected/tagged, ':' runs one command for each tagged item; htop's Space/c tag a row or a subtree and F9 acts on the set.** — A prompt tree with forks is a tree; a fleet of agents is a tree. Tag-then-verb (deny all tagged, raise budget on tagged, replay from tagged checkpoint) scales the operator's intent without a modal dialog per item, and a format-expression filter ('show me every pane whose last verdict was deny') is cheaper than a query language. [https://man.openbsd.org/tmux (choose-tree) and https://man7.org/linux/man-pages/man1/htop.1.html]
- **Named 'screens' over one live table, each with its own columns, sort key, tree flag and collapse state, cycled with Tab and persisted as plain lines (screen:Main=PID USER ... then .sort_key= .tree_view= .sort_direction= .all_branches_collapsed=).** — The garden and the fleet are the same rows seen through different lenses (by agent, by pathway, by tokens saved, by verdict). Persisting each lens as a few key=value lines keeps them diffable and shareable, which is the one thing btop's auto-rewritten config gets wrong. [https://raw.githubusercontent.com/htop-dev/htop/main/Settings.c]
- **Control-mode discipline for the wire: every command reply framed by %begin/%end/%error with timestamp and command number, per-pane %output deltas, structural notifications (%window-add, %window-close, %session-changed), client-declared backpressure ('refresh-client -f pause-after=30' then %pause / continue), and named subscriptions ('refresh-client -B name:what:format') that report changes at most once a second.** — For a cockpit fed by many agents, these are the four things that keep the UI from falling behind: framed replies (so verdicts pair with proposals), deltas not snapshots, explicit pause/resume per source, and rate-limited derived values (budgets, token counts) instead of polling. [https://github.com/tmux/tmux/wiki/Control-Mode]

## avoid
- **Global single-modifier keybindings that collide with the programs inside (zellij default Ctrl g/Ctrl p/Ctrl r/Alt keys hijack shell reverse-search, vim, macOS Alt).** — Issue #1399 'Improve default keybindings' has 52 comments and is still open since 2022; #532 'Hijacked CTRL+R' and #418 'Unable to send ctrl-g' show the cost. zellij had to ship a whole second preset (unlock-first) and a locked mode to compensate. A cockpit that hosts agent terminals must start from a prefix or lock-first model, not from bare Ctrl chords. [https://github.com/zellij-org/zellij/issues/1399]
- **Chrome the operator cannot remove: two status lines, pane frames and a 'zellij' brand mark by default; htop's function bar likewise needed an explicit --no-function-bar flag (3.5.0) years later.** — The FAQ's own entry is 'The UI takes up too much space, what can I do about it?'; 0.45 turned frames off by default in response, and HN readers still asked why the branding cannot be removed. Every persistent row in a supervision cockpit must be optional from day one, with the hint layer available as a tooltip. [https://zellij.dev/documentation/faq.html and https://hn.algolia.com/api/v1/items/49373884]
- **Persistence hung on a UI side-effect: tmux-continuum autosaves by inserting itself into status-right, so a theme plugin that overwrites status-right silently stops saving; the docs' fix is 'put continuum last'.** — Checkpointing agent sessions must be a daemon/gate responsibility with its own timer (zellij's serialization_interval model), never a hook riding on whatever draws the status bar. [https://github.com/tmux-plugins/tmux-continuum]
- **'Resurrection' that replays commands instead of restoring state: tmux-resurrect re-runs saved command lines via send-keys, only for an allowlist (@resurrect-processes), losing environment (#94), wrapper commands (#44) and cluttering history (#86); zellij mitigates the safety side with the ENTER banner but has the same information loss.** — For a prompt tree with time travel, replay-from-command-line is the wrong data model; checkpoints must capture the conversation state (the prefix) itself, and any replay must be gated exactly as a new action would be. [https://github.com/tmux-plugins/tmux-resurrect/issues/44]
- **Apps that rewrite their own config file on every UI action (btop) or declare the file must not be hand-edited (htop: 'overwritten upon clean exit ... so it should not be hand-edited').** — Operators put cockpit config under version control; HN's petepete: 'anything you do in the application results in config file changes'. Keep a read-only declarative config (KDL/TOML) and a separate per-user state file for ephemeral view state. [https://hn.algolia.com/api/v1/items/45856987]

## loadBearingClaims
- zellij exposes a machine-readable control plane: 'zellij action list-panes --json' returns pane objects with stable ids (terminal_N / plugin_N), most actions accept --pane-id without changing focus, and 'zellij subscribe --pane-id X --format json' streams NDJSON events {event: pane_update, pane_id, viewport[], scrollback, is_initial} and {event: pane_closed}. [https://zellij.dev/documentation/programmatic-control.html]
- zellij serializes every session to a human-readable KDL layout every 1 s in the cache folder, and resurrected command panes do not run until the user presses ENTER ('Press ENTER to run...' banner; --force-run-commands to skip). [https://zellij.dev/documentation/session-resurrection.html]
- tmux control mode frames each command reply with %begin/%end/%error, streams pane content as %output deltas, supports client backpressure via 'refresh-client -f pause-after=N' (%pause / %continue) and format subscriptions via 'refresh-client -B name:what:format' reported by %subscription-changed at most once a second. [https://github.com/tmux/tmux/wiki/Control-Mode]
- zellij plugins are WASM/WASI with a per-capability permission prompt (ReadApplicationState, ChangeApplicationState, RunCommands, WriteToStdin, ReadPaneContents, InterceptInput, RunActionsAsUser, ...) and can observe every user action (UserAction), rendered pane text (PaneRenderReport) and per-pane foreground command changes (CommandChanged). [https://zellij.dev/documentation/plugin-api-events.html]

## verification
- [qualified] zellij exposes a machine-readable control plane: 'zellij action list-panes --json' returns pane objects with stable ids (terminal_N / plugin_N), most actions accept --pane-id without changing focus, and 'zellij subscribe --pane-id X --format json' streams NDJSON events {event: pane_update, pane_id, viewport[], scrollback, is_initial} and {event: pane_closed}. — The subscribe part is confirmed verbatim on the dedicated page https://zellij.dev/documentation/zellij-subscribe.html (the cited programmatic-control page defers to it): `{"event":"pane_update","pane_id":"terminal_1","viewport":["line1","line2"],"scrollback":null,"is_initial":true}` and `{"event":"pane_closed","pane_id":"terminal_1"}`; `-p, --pane-id` is 'required, repeatable', `-f, --format` is 'raw (default) or json', `-s, --scrollback [LINES]` adds scrollback to the initial delivery only ('no scrollback on subsequent deliveries'; null otherwise), 'Subsequent deliveries occur only when the viewport content changes. Only changed viewports are sent' (whole viewport, not line deltas), ANSI stripped unless `--ansi`, and 'The client exits automatically when all subscribed panes have been closed or the session ends.' Shipped in v0.44.0 (GitHub release 2026-03-23: 'zellij subscribe ... optionally in --json format'; 'zellij action list-panes ... Also optionally in --json format'). ID shape is where the claim slips: the string ids `terminal_N`/`plugin_N` are what the CLI prints and what `--pane-id` accepts (data.rs `impl Display for PaneId` writes `terminal_{}`/`plugin_{}`; FromStr also accepts a bare number), but `list-panes --json` objects carry a bare integer `id` plus `is_plugin` (cli-actions sample: `"id": 1, "is_plugin": false, "is_focused": true, ...`; data.rs `pub struct PaneInfo { pub id: u32, pub is_plugin: bool, ... }`). The cited page's own recipe has to strip the prefix to join them: `jq -r ".[] | select(.id == ${PANE_ID#terminal_}) | .exited"`. On focus: https://zellij.dev/documentation/cli-actions.html lists 28 actions with `--pane-id` (clear, close-pane, dump-screen, edit-scrollback, page/half-page/scroll-*, move-pane[-backwards], paste, rename-pane, resize, send-keys, set-pane-borderless, set-pane-color, toggle-fullscreen, toggle-no-ui-fullscreen, toggle-pane-*, write, write-chars) but never says targeting by id leaves focus alone; the 'without changing the focus of any client' wording exists only for `--no-focus` on new-pane/new-tab/launch-plugin. The source does show write/paste-by-id are focus-neutral (route.rs `Action::WriteCharsToPaneId → ScreenInstruction::WriteToPaneId`; screen.rs finds the tab with `has_pane_with_pid` and calls `tab.write_to_pane_id(...)`, no focus change), but that is code behaviour, not a documented contract, and was not checked for every action. - [qualified] tmux control mode frames each command reply with %begin/%end/%error, streams pane content as %output deltas, supports client backpressure via 'refresh-client -f pause-after=N' (%pause / %continue) and format subscriptions via 'refresh-client -B name:what:format' reported by %subscription-changed at most once a second. — The cited wiki supports the framing and flow control: 'Every command produces one block of output. - [qualified] zellij plugins are WASM/WASI with a per-capability permission prompt (ReadApplicationState, ChangeApplicationState, RunCommands, WriteToStdin, ReadPaneContents, InterceptInput, RunActionsAsUser, ...) and can observe every user action (UserAction), rendered pane text (PaneRenderReport) and per-pane foreground command changes (CommandChanged). — Runtime: https://zellij.dev/documentation/plugins.html says 'Zellij offers a Webassembly / WASI plugin system, allowing plugin developers to develop plugins in many different languages' ('Currently, Rust is the only language officially supported'). Permissions (https://zellij.dev/documentation/plugin-api-permissions.html) list ReadApplicationState, ChangeApplicationState, OpenFiles, RunCommands, OpenTerminalsOrPlugins, WriteToStdin, Reconfigure, FullHdAccess, StartWebServer, InterceptInput ('Intercept user input (eg. keypresses), having all of this input sent to the plugin instead'), ReadPaneContents ('Required for subscribing to the PaneRenderReport event'), RunActionsAsUser ('Required for the run_action plugin API command'), WriteToClipboard, ReadSessionEnvironmentVariables. Events (cited page): `Event::UserAction(Action, ClientId, Option<u32>, Option<ClientId>)` - 'Required Permission: InterceptInput ... Fired when any action is performed by a user. This is useful for observing all user activity in the session'; `Event::PaneRenderReport(HashMap<PaneId, PaneContents>)` - 'Required Permission: ReadPaneContents ... rendered content of subscribed panes with ANSI escape codes stripped. This event is fired periodically for panes the plugin has subscribed to observe' (screen.rs drains it on every render and sends `PluginInstruction::PaneRenderReport`); `Event::CommandChanged(PaneId, Vec<String>, bool, Vec<ClientId>)` - 'Required Permission: ReadApplicationState ... Fired when the foreground command running inside a terminal pane changes (for example when a user runs vim from a shell, or when that program exits...)'. Qualifications: (1) 'per-capability prompt' overstates it - `request_permission(permissions: &[PermissionType])` takes the whole set in `load`, 'The user will be prompted to grant or deny the requested permissions', and the answer is a single `PermissionRequestResult(PermissionStatus::Granted | Denied)`; it is one prompt per plugin covering all requested permissions, not a separate yes/no per capability. (2) CommandChanged is brand new: v0.45.0 release notes (2026-08-20) 'New events include CommandChanged, InitialKeybinds, HostTerminalThemeChanged...' - absent in 0.44.x. (3) 0.45.0 also removed `PaneRenderReportWithAnsi`; 'the plain-text PaneRenderReport remains', so a plugin cannot get styled pane text via this event. (4) Observing UserAction requires InterceptInput, the same permission that allows swallowing keystrokes (`intercept_key_presses`), so a read-only supervision plugin must ask for the most invasive permission. → corrected: zellij plugins are WebAssembly/WASI (Rust officially supported) gated by a permission system; a plugin requests a set of permissions once via request_permission(&[...]) and the user grants or denies that whole set in one prompt (single Granted/Denied result), not per capability. Permissions include ReadApplicationState, ChangeApplicationState, OpenFiles, RunCommands, OpenTerminalsOrPlugins, WriteToStdin, Reconfigure, FullHdAccess, StartWebServer, InterceptInput, ReadPaneContents, RunActionsAsUser, WriteToClipboard, ReadSessionEnvironmentVariables. With InterceptInput a plugin receives UserAction for every user action; with ReadPaneContents it receives PaneRenderReport (plain text only since 0.45.0, per render, for panes it subscribed to); with ReadApplicationState it receives CommandChanged (new in v0.45.0, 2026-08-20) when a pane's foreground command changes.
