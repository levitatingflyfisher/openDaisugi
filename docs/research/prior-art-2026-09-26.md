# Prior art: skills, library learning, policy languages, runtime assurance

Date: 2026-09-26; section 6 added 2026-09-27. Method: WebSearch and WebFetch. Every outside claim cites a page that was
fetched and read in this pass. Where only an abstract was read, the claim stays at abstract
depth. This survey adds to `docs/research/formal-methods-2026-09-23.md` (Progent, AgentCore,
AgentSpec, ShieldAgent, ContrAgent, shell semantics). It does not repeat that report's findings
except where a neighbour matters for the dialect idea in
`docs/plans/2026-09-24-omarchy/strategy-2026-09-26.md`.

## Summary

- Skill and workflow learners (Voyager, AWM, Memp, SkillGen, SkillForge, SkillOps) learn from
  trajectories and reuse by retrieval. When they say "verified", they mean "it helped the task
  succeed". None of them proves a skill safe before reuse.
- Skill marketplaces are a live attack surface. One study found a vulnerability in 26.1% of
  31,132 skills. Anthropic tells users to audit skills by hand.
- Library learning (DreamCoder, Stitch, LILO, babble) compresses programs into named
  abstractions. Stitch is MIT and was maintained this month. Three 2024-2026 papers show that
  LLM "library learning" often does not reuse its library at all.
- Model-written policies checked by a solver are now common: Progent, ActGov, VeriGuard, a Z3
  compliance checker on tau2-bench, Agent-C, AgentCore on Cedar. Most check the policy once, at
  authoring time. Few prove each action. None learns a vocabulary of named, proved words.
- Few 2024-2026 papers on LLM agents name the Simplex lineage. Robotics work is closest.
- Imp ports DSPy to Elixir and runs agents as supervised processes. Its tool calls pass an
  `authorize` callback, and a failed tool call has an outcome class (refused, not sent,
  unknown). GEPA, one of its optimizers, rewrites prompts from reflection on failures. We
  borrow four ideas from them and plan one adapter (section 6, added 2026-09-27).

## 1. Skill libraries and workflow learning

| System | Learns | From | Reuse | Checked before reuse |
|---|---|---|---|---|
| Voyager (2023) | executable code skills | environment feedback, execution errors, self-verification | retrieval into new tasks and worlds | self-verification of success; no safety check |
| Agent Workflow Memory (2024) | "commonly reused routines" | offline examples or online test queries | workflows given to the agent as guidance | abstract names no filter |
| Memp (2025) | step instructions and "script-like abstractions" | past trajectories | retrieval; memory is updated, corrected, deprecated | no safety check named |
| SkillGen (2026) | one auditable skill (prompt, scripts, docs) | successful and failed trajectories, contrasted | loaded into context | paired A/B on the same inputs; deploy only on positive net effect |
| SkillForge (2026) | decision guidelines | RL training episodes | skill bank | EMA success rate per skill; poor skills revised |
| SkillOps (2026) | library maintenance | the library itself | merge duplicates, add validators, insert adapters | functional validators; no permission checks |
| Anthropic Agent Skills (Oct 2025) | nothing learned; human or model authored | procedural knowledge | progressive disclosure: metadata, then SKILL.md, then files | "install skills only from trusted sources" |

Sources: Voyager, https://arxiv.org/abs/2305.16291. AWM, https://arxiv.org/abs/2409.07429.
Memp, https://arxiv.org/abs/2508.06433. SkillGen, https://arxiv.org/html/2605.10999v1 (code at
github.com/yccm/SkillGen, license not checked). SkillForge, https://arxiv.org/html/2608.24747.
SkillOps, https://arxiv.org/html/2605.13716v1. Agent Skills,
https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills.

SkillGen is the nearest to the garden's promotion step. It counts "repairs" and "regressions"
on identical inputs and marks a skill "deprecated" when the net gain is below a threshold
(https://arxiv.org/html/2605.10999v1). SkillForge says plainly that its verification is
performance evidence, not safety (https://arxiv.org/html/2608.24747).

**The safety gap is measured.** A study of 31,132 skills from two marketplaces found that 26.1%
hold at least one vulnerability and 5.2% show high-severity patterns. Skills that bundle scripts
are 2.12 times more likely to be vulnerable (https://arxiv.org/abs/2601.10338). A 2026 SoK
reports a campaign of 1,184 malicious skills in the OpenClaw registry. It says tier changes
"should be enforced by the runtime, not by skill-provided metadata", and it lists formal
verification across skill encodings as an open problem (https://arxiv.org/html/2602.20867v1).
In Claude Code, a skill's `allowed-tools` field pre-approves tools for one turn. The docs warn
that "a skill can grant itself broad tool access" and that workspace trust does not gate the
field (https://code.claude.com/docs/en/skills).

For openDaisugi: a pathway today carries an envelope that the gate checks before each step
(`src/opendaisugi/pathway.py`, `src/opendaisugi/distiller.py`). The distiller intersects the
permissions of a cluster of traces, and verifies the template against held-out traces (`src/opendaisugi/distiller.py`). Pathway
bundles are signed (`src/opendaisugi/signing.py`, `src/opendaisugi/pathway_bundle.py`). That is a safety
check on the skill, not only a success check. We found no skill learner above that does this.

## 2. Library learning

| Tool | Idea | License | Maintenance (GitHub API, 2026-09-26) |
|---|---|---|---|
| DreamCoder (`ellisk42/ec`) | wake-sleep library learning | MIT | last push 2023-07-01 |
| Stitch (`mlb2251/stitch`) | top-down search for abstractions over lambda terms | MIT | last push 2026-09-08; commits in 2025-09 made compression resumable |
| stitch_bindings (`stitch_core` on PyPI 0.1.29) | Python bindings to Stitch | no LICENSE file and no license metadata found | last push 2025-10-08 |
| LILO (`gabegrand/lilo`) | LLM synthesis + Stitch + AutoDoc naming | MIT (stated in README; no LICENSE file) | last push 2024-08-29 |
| babble (`dcao/babble`) | library learning modulo an equational theory, with e-graphs | MIT | last push 2023-05-31 |

Stitch is "3-4 orders of magnitude faster" than DreamCoder's compressor with "2 orders of
magnitude less memory" and comparable compression (https://arxiv.org/abs/2211.16605). Its input
is JSON lists of s-expressions with de Bruijn indices, and it has Python bindings
(https://github.com/mlb2251/stitch). LILO adds AutoDoc, which writes names and docstrings from
usage examples. We found no step that checks a name against its meaning
(https://arxiv.org/abs/2310.19791). babble takes an equational theory as input and uses
e-graph anti-unification (https://arxiv.org/abs/2212.04596). Leroy wraps Stitch for imperative
languages by converting ASTs to a Lisp-like form (https://arxiv.org/html/2410.06438v1).

**The sceptics.** "Library Learning Doesn't" finds that function reuse in LEGO-Prover and TroVE
is "extremely infrequent", and that self-correction and self-consistency drive the gains
(https://arxiv.org/abs/2410.20274). A LEGO-Prover case study finds "no evidence of the direct
reuse of learned lemmas", and the gains vanish once compute is counted
(https://arxiv.org/abs/2504.03048). The EACL 2026 paper asks for equal compute budgets and
behavioural checks that the library is actually used
(https://aclanthology.org/2026.eacl-long.163/).

**Policy mining is library learning for access control.** LLMs mine compact ABAC policies at
small scale, but accuracy falls and policy size grows as subjects and objects increase. The
authors suggest a hybrid with classical rule mining (https://arxiv.org/abs/2511.18098).
KBSpec grows a knowledge base from verifier feedback on JML specifications and raises pass
rates by 14-32% (https://arxiv.org/abs/2606.21339). That is a growing vocabulary for
specifications, but checked by a verifier on programs, not on agent actions.

For openDaisugi: the 2026-09-26 first test (strategy notes, "Dialects") used a greedy pass over
flat permission sets. Stitch is the obvious next tool: MIT, Rust, maintained, with a JSON input
we can emit from envelopes as trees. The sceptics set the bar for our own claim: measure that
dialect words are reused on held-out envelopes, and count the cost.

## 3. Model-written policies and verified guardrails

### Languages built for analysis

- **Cedar.** The design is "finely balanced to allow for a sound and complete logical
  encoding" (https://arxiv.org/abs/2403.04651). `cedar-policy-symcc` compiles policies to
  SMT-LIB and checks never-errors, always-allows, always-denies, subsumption, equivalence and
  disjointness, each with a counterexample. It uses cvc5 1.3.1, and the compiler and verifiers
  are "formally modeled and verified in Lean"
  (https://github.com/cedar-policy/cedar/tree/main/cedar-policy-symcc). Cedar and cedar-spec are
  Apache-2.0 and were pushed on 2026-09-25 (GitHub API). AWS AgentCore uses Cedar for agent tool
  calls; see finding 4 of `docs/research/formal-methods-2026-09-23.md`.
- **OPA/Rego.** Rego is "inspired by Datalog" and extended for JSON; `opa test` runs unit tests
  (https://www.openpolicyagent.org/docs/policy-language). The page we read says nothing about
  formal analysis. LLM-to-Rego pipelines check with lint, compile and generated tests, not
  proofs: one reaches 50.3% end-to-end correctness against 15.3% for a direct prompt
  (https://arxiv.org/abs/2609.24036). OPA is Apache-2.0 and active (GitHub API).

### Models write the policy, a solver checks it

| Work | Who writes | What the solver checks | When |
|---|---|---|---|
| Progent (2025) | LLM writes and updates policies from the task | Z3 decides if an update narrows (automatic) or widens (needs approval): "monotonic confinement" | at each policy update; runtime is deterministic rule checks |
| ActGov (Sep 2026) | LLM drafts rules from tool specs, benign traces and attack failures | Z3 searches for a record that satisfies the policy but breaks a safety assertion | offline, per policy update; runtime checks finite records |
| Solver-aided compliance (2026) | experts with LLM help; full automation "proved inadequate" | Z3 per planned tool call; an LLM extracts the values; unsat core goes back as the reason | per call, before it runs |
| VeriGuard (Oct 2025) | LLM writes a policy function and its constraints | Nagini proves the policy code meets its pre/postconditions | offline; runtime runs the proved policy |
| Agent-C (Dec 2025) | a temporal DSL, lowered to first-order logic | SMT during decoding; constrained generation of a compliant call | per token, per call |
| C-Trace (Jun 2026) | developers | first-order GDPR predicates over the event stream | per call, before it runs |
| AgentSpec (ICSE 2026) | humans, or o1 (95.56% precision, 70.96% recall) | Python predicates, no solver | per event |

Sources: Progent, https://arxiv.org/abs/2504.11703. ActGov, https://arxiv.org/abs/2609.24446 and
https://arxiv.org/html/2609.24446v2. Solver-aided compliance,
https://arxiv.org/html/2603.20449v1. VeriGuard, https://arxiv.org/html/2510.05156. Agent-C,
https://arxiv.org/abs/2512.23738. C-Trace, https://arxiv.org/html/2606.19242v1. AgentSpec,
https://arxiv.org/abs/2503.18666.

Numbers worth keeping. ActGov reports attack success at or below 0.007 on AgentDyn and 0.000 on
AgentDojo; its policy language is Boolean logic over finite enumerated values in three levels
and seven scopes (https://arxiv.org/html/2609.24446v2). The solver-aided checker cut invalid
write calls on tau2-bench airline to 29% from about 50%
(https://arxiv.org/html/2603.20449v1). Agent-C raised conformance for Claude Sonnet 4.5 from
77.4% to 100% (https://arxiv.org/abs/2512.23738). No public code was named for ActGov, Agent-C or
the solver-aided checker.

### Capabilities and information flow

CaMeL extracts control and data flow from the trusted query so untrusted data cannot steer the
program, and checks capability policies at tool calls. It solved 77% of AgentDojo tasks "with
provable security" against 84% undefended. Code is released under CC BY 4.0
(https://arxiv.org/abs/2503.18813).

## 4. Runtime assurance for AI agents since 2024

The robotics side is closest to Simplex, but the papers we read do not use the name.

- RoboGuard uses a "root-of-trust LLM" to ground fixed safety rules into temporal logic for the
  scene, then uses control synthesis to repair unsafe plans. Unsafe plan execution fell from
  over 92% to below 3% (https://arxiv.org/abs/2503.07885).
- A reachability paper checks LLM commands against data-driven reachable sets. The abstract
  names no fallback controller (https://arxiv.org/abs/2503.03911).
- An ICRA 2026 agriculture paper has one LLM write LTL and a second check it, for mission plans
  (https://arxiv.org/abs/2606.18519).
- A May 2026 position paper argues for three assurance layers (user, operational, functional)
  with probabilities that compose by the chain rule. It has no implementation and does not
  cite Simplex (https://arxiv.org/html/2605.18672).
- A September 2026 survey of AI network control loops calls runtime assurance "the missing
  layer" and proposes dependency-aware assurance. The abstract does not cite Simplex
  (https://arxiv.org/abs/2609.11996).
- ADMITBench (Aug 2026) checks industrial LLM advice with "explicit, non-compensatory checks"
  and does not authorise execution (https://arxiv.org/abs/2608.03866).

The theory preprint on what a pre-execution gate can enforce, and ContrAgent's trajectory
contracts, are in `docs/research/formal-methods-2026-09-23.md` (findings 5 and 6).

## 6. Imp and GEPA (added 2026-09-27)

### Imp

Imp (`deepfates/imp`) is "a full port of DSPy to the BEAM", written in Elixir
(https://github.com/deepfates/imp). The GitHub API gives MIT and a creation date of
2026-07-10 (https://api.github.com/repos/deepfates/imp, read 2026-09-27). What it has, from
the README:

- **Signatures and modules.** "You describe what each language-model step takes and
  returns." A signature such as `issue -> kind: enum[bug,feature,question], summary` is
  checked against the reply, which comes back as typed fields.
- **Optimizers.** GEPA, MIPROv2, SIMBA, few-shot bootstraps and fine-tuning. GEPA "runs the
  program, reads where it failed, and rewrites its instructions", and it works on whole
  agent runs too.
- **Agents as processes.** `Imp.start_run/3` runs a program as "its own supervised
  process", so a host can "watch it, stop it, and decide which tool calls it may make". The
  last part is an `authorize: fn call -> ... end` option that returns `:allow` or
  `{:deny, reason}`.
- **MCP and ACP.** It imports the tools of an approved MCP server and serves any Imp program
  as an ACP agent to Zed and other ACP clients.
- **A tool call that may have run is not retried.** "A tool call that may already have
  taken effect is reported as unknown, never silently retried."
- **Status.** The README calls Imp 0.5 "experimental" and says "its optimizers need
  large-scale benchmarking".

Its CI has a differential lane that "validates Imp against real pinned DSPy 3.2.1"
(https://github.com/deepfates/imp/blob/main/.github/workflows/ci.yml). That is the same
method as our clients against the Python oracle (`docs/spec/conformance.md`).

Its `decisions.md` is a ledger with one row per ruling. Each row has a date, the source and
reason, a **Status** ("In force", "Retired 2026-09-23 by the row below") and a **Retires
when** ("Does not retire", or a named condition) (https://github.com/deepfates/imp/blob/main/decisions.md).
Retired rows stay in the table. The ledger also records the outcome classes. An MCP tool
call that got no answer "returns `%Imp.MCP.CallFailure{}` with an `outcome` of `:refused`,
`:not_sent` or `:unknown`", and "A timeout is always `:unknown`". A second row says a tool's
return value alone never reads as refused, because "`:refused` tells a caller that
repeating the call is safe" (same URL, rows dated 2026-09-24 and 2026-09-25).

### GEPA

"GEPA: Reflective Prompt Evolution Can Outperform Reinforcement Learning", Agrawal et al.,
arXiv 2507.19457, v1 25 July 2025 (https://arxiv.org/abs/2507.19457). From the abstract:
GEPA samples trajectories (reasoning, tool calls, tool outputs), reflects on them in natural
language, proposes and tests prompt updates, and combines lessons "from the Pareto frontier
of its own attempts". Across six tasks it beats GRPO "by 6% on average and by up to 20%,
while using up to 35x fewer rollouts", and beats MIPROv2 "by over 10%". The code is
`gepa-ai/gepa`, MIT (GitHub API, read 2026-09-27). We read the abstract only.

### What we borrow, and one adapter we plan

| Idea | From | Where it goes in openDaisugi |
|---|---|---|
| A "Status" and a "Retires when" on every ruling | Imp `decisions.md` | `clients/ADJUDICATIONS.md` and `docs/plans/2026-09-24-omarchy/DECISIONS-PENDING.md` (done 2026-09-27) |
| Tool outcome classes: refused, not sent, unknown | Imp `CallFailure` | the journal records the class of each tool call; "unknown" goes to receipts and rollback (`src/opendaisugi/deeds.py`), never to a retry. Designed, not built (roadmap problem 3) |
| Signatures as the language of small-model steps | Imp, after DSPy | the typed steps a cheap model runs under the router (roadmap problem 4) and in envelope generation (stage K1). Designed, not built |
| GEPA with the verifier as its metric | GEPA | the garden's optimizer, scored by proofs, tests and gate verdicts. Designed, not built (roadmap problem 5) |
| An Imp gate adapter | Imp `authorize` | an `authorize` function that asks the resident gate over its socket (`src/opendaisugi/gate_server.py`, `daisugi gate serve` in Go and Rust). Designed, not built (roadmap problem 3) |

### How we differ

- **A proof, not host code.** Imp's `authorize` is a function the host writes. daisugi
  proves each call against an envelope with Z3 (`src/opendaisugi/gate.py`). An Imp adapter
  would put that proof behind Imp's callback.
- **Fail closed.** Imp's ledger records that a misspelled `:authorize` "ran tools
  unauthorised", now caught by option checks (row dated 2026-09-25). We did not verify what
  a run with no callback does. daisugi denies on every failure path, including a gate that
  does not answer (`src/opendaisugi/gate_client.py` falls back to the in-process gate, never
  to allow).
- **The metric.** GEPA's reported gains are task scores. In the garden, a candidate prompt
  must also keep every proof, test and gate verdict; a higher score with a new deny is a
  loss. The library-learning sceptics (section 2) set the same bar: count compute and
  measure on held-out work.
- **The cost.** A GEPA run spends model calls. On this box it is a heavy job and falls under
  the owner's rules: about ten short live sessions a day, and one heavy job at a time.
- **Scope.** Imp is a library for writing model programs. daisugi is a gate and a garden
  for agents that other harnesses run. The two can meet at the `authorize` callback.

## Where we are behind

- **Envelope lint.** Cedar SymCC checks always-allows, always-denies, equivalence and
  disjointness, with counterexamples, and its encoder is proved in Lean. openDaisugi has
  tautology and contradiction checks per predicate (`src/opendaisugi/vacuity.py`) and
  subsumption (`src/opendaisugi/subsumption.py`). It has no proof that its own encoding is
  correct; it relies on differential testing across clients.
- **Temporal properties.** Agent-C, C-Trace and ContrAgent check order and history. The
  envelope is per step. `Before` and `DependsOn` exist at plan level
  (`src/opendaisugi/vacuity.py` names them), but the gate does not check across a session.
- **Outcome evidence.** SkillGen's paired repair-vs-regression count is more careful than a
  held-out pass rate. The garden should report both.
- **Benchmarks.** The neighbours report AgentDojo, AgentDyn, ASB and tau2-bench numbers.
  openDaisugi reports none. Its numbers come from synthetic cases (strategy notes, "The worry").
- **Adversarial skills.** 26.1% of marketplace skills are vulnerable. We have not tested the
  gate against a corpus of malicious skills.

## Where we may be first

We did not find these above. "Not found" is not "does not exist".

1. **Learned, proved dialects for agent policy.** Library learning over the policy language that
   governs actions, with Z3 proving word equivalence over a fixed decidable kernel. KBSpec grows a
   vocabulary for program specs; ABAC mining learns policies; neither learns named words over a
   kernel.
2. **Skills that must fit an envelope before reuse.** Every skill learner we read checks success.
   The distiller checks permissions and verifies against held-out traces
   (`src/opendaisugi/distiller.py`).
3. **One kernel from coding agents to robots.** The policy work is about tool-using software
   agents; the robotics work is about robots. We found no system that gates both with one
   verifier.
4. **Per-action SMT proof across harnesses, with a journal feeding a distiller.** ActGov and the
   solver-aided checker are closest. Neither has a garden.

## What we could not verify

- Full texts: most rows rest on abstracts. ActGov, VeriGuard and the solver-aided checker were
  read in more depth.
- Licenses of `stitch_bindings` / PyPI `stitch_core` (no license found), SkillGen, and the
  missing code of ActGov and Agent-C.
- Black-Box Simplex (Springer) did not load, so no claim about its 2024 multi-agent version is
  made here.
- Whether any lab product (for example AgentCore) learns policy vocabularies. We found no
  statement either way.
- Whether a 2026 Simplex-for-LLM-agents paper exists that our searches missed. Two searches
  found only robotics, CPS and position papers.
