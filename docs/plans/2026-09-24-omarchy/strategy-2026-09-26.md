# Strategy notes, 2026-09-26

The owner and the build session talked through where openDaisugi stands and where it goes.
This file records the conclusions and the open questions. It is a record of thinking, not a
spec. Decisions that need the owner are marked **Open**.

## What openDaisugi is

The throughline has not changed since the whitepaper: **separate what is allowed from what is
decided.** A model decides. An envelope says what is allowed. A proof checks each action against
the envelope before it runs.

The JIT compiler analogy still holds, and it fits better now than when it was first used:

| JIT part | openDaisugi part |
|---|---|
| Interpreter (slow, general, always works) | the frontier model, reasoning from scratch |
| Profiler | the journal: every action, verdict and token |
| Tiered compilation | the routing ladder: pathway (0 tokens), local model, warm cache, cheap model, frontier |
| Profile-guided optimizer | the garden, which compiles repeated work into pathways |
| Type checker | Z3 and the envelope, before anything runs |
| Deoptimization | fail closed: a failed proof falls back to the frontier or to a human |
| The runtime's sandbox | the gate |
| Debugger and console | coppice |

A pitch in one breath: *openDaisugi is a JIT compiler for AI agents. The first time, a frontier
model does the work and a formal proof checks every action before it runs. The tenth time, it
runs as a verified script for free. One gate, whether the agents write code or fly drones.*

## The bitter lesson

The bitter lesson is against over-specialization, not against efficiency. A pathway is a
specialization the system earns from its own journal and drops when it stops being true. So the
"specialize, bundle, unbundle" cycle runs automatically on the owner's own work. Compute and data
make it better; hand-tuning does not.

**Owner ruling: the bots write the policy.** No one will learn an envelope language. Models write
envelopes, rules and grafts; the proofs are mechanical; the human sets a ceiling and reviews.

## Models writing languages for a situation

The early dream was that models are good at writing a small language for one situation, and a
simple checked system runs inside it (runtime assurance pattern 4, "compiled policy / live DSL",
in the whitepaper). It was not lost. The envelope and the predicate algebra are that language,
and Z3 is only the checker under it. But the language is fixed today: one grammar for every
situation.

The insight left to mine: let the model write the **vocabulary** for a situation, not only the
sentences. For example a model defines "a safe git operation" or "a read-only deploy check" as a
new named predicate built from existing ones, and the verifier proves the new word means what
its definition says. Words that prove useful across many tasks become part of the shared
vocabulary. This is distillation applied to the policy language itself. **Open:** worth a
design, after the dogfood week.

## Dialects: one kernel, many languages

**The owner's breakthrough, 2026-09-26.** openDaisugi was pictured two ways that seemed not to
meet: safe "muscle memory" for robot swarms, at the level of one robot and of the whole
population, and a few agents running a software startup. Both get the same guarantees because a
proof is universal. What differs is the vocabulary. So:

- **One kernel.** The predicate algebra stays small, fixed and decidable, as Cedar's language is
  designed for sound and complete SMT analysis. The kernel is where the guarantees live.
- **Many dialects.** Each domain gets a vocabulary of named words defined only in kernel terms:
  `safe_git_op`, `no_prod_write` for a software team; `keep_separation(d)`,
  `within_geofence(zone)`, `grip_force_below(n)` for a swarm. A word unfolds to the kernel, so
  every question stays decidable. The dialect carries the domain's assumptions, the way a good
  DSL does, so it is precise and a reader sees what it can and cannot say.
- **Models write and grow the dialect; humans read it; Z3 checks the unfolded kernel.** No one
  learns a DSL by hand. The garden mines the journal for repeated sub-predicates, a model names
  them in plain words, and Z3 proves two words equal so the vocabulary does not grow duplicates.
  This is library learning (DreamCoder, Stitch, LILO; babble does it modulo an equational
  theory with e-graphs) applied to the policy language.
- **Muscle memory at two levels.** A pathway written in the dialect is one agent's or one
  robot's learned skill. A word that proves useful across the population joins the shared
  dialect. The dialect is the population's culture; the kernel is its physics.
- **Dialects meet at the kernel.** A word from one dialect can be checked against a word from
  another, because both unfold to the same kernel. Two teams, or a drone team and a warehouse
  team, can prove their policies agree.

What is not new: fixed kernels, macros over them, and library learning are known ideas. What may
be new: learned, proved, per-domain dialects for the policy that governs agent actions, with one
kernel from a software team to a robot swarm.

Honest limits: the kernel must say enough for each domain. Robot dynamics bring nonlinear real
arithmetic, where Z3 can answer "unknown", and the gate then fails closed. A dialect word is only
as trustworthy as its definition, which Z3 checks, and as its name, which a model chose; a
misleading name is a real risk, so names should be checked against the definition.

**The first test (cheap):** run a compression pass over real envelopes and pathways (the owner's
gate root and pathway store, read only, with consent) and see whether shared sub-predicates
appear and how much they compress. If real policies compress, dialects are real. If they do not,
the idea waits for more data.

**First test result (2026-09-26).** A copy of the owner's journal (740 traces, 294 distinct
envelopes from real tasks; 416 test traces with the task "t" left out) was scanned. Only the
permission sets were used, as flat sets of atoms (a shell command, a read or write glob, a host);
invariants and plan trees were not. A greedy pass that names repeated sets cut the size from 2,769
atoms to 2,284, including the word definitions: 17.5% with 15 words. The words read like a
dialect:

- `cat find grep head tail` (25 envelopes): read-only inspection.
- `make npm pytest python` (21): build and test.
- `f-droid.org github.com gitlab.com`, network on (17): code forges and app stores.
- `**/*.json **/*.yaml **/*.yml` (16): config files.
- read and write `lib/** src/**` (9): the source tree.
- `developer.android.com developer.apple.com material.io nngroup.com` (7): design references.
- A repeated invariant, "must not modify <target>", is a word with a parameter.

Limits: small data, flat sets only, and a greedy pass, not Stitch's search over trees. Postconditions
are mostly `exit_code` (146) and `file_exists` (39), so the policies today are mostly allowlists.
The result says the dialects are there in the data, even for a mostly development workload with
some research agents mixed in. The next test runs a real compressor (Stitch) over envelopes and
plans as trees.

## What weave was for

Recovered from the August session that built sprig, grove and weave. The owner, 2026-08-26, on
weave's real ancestor: "the directed graph of distilled actions, each steps some of which are
more deterministic and scripty and some of which are LLM based small model with constrained
token grammar output and some of which are large very wide open bleeding edge", and "LLMs are
esp good at ON THE FLY DSLs". The design called weave "the harness home for the ADR-0008 idea
(parameterized, callable, composable pathways)", with `step`, `parallel`, `gate` and `on-fail`.
What was built is a 131-line runner of a JSON graph that runs steps one at a time and stops at
the first failure. Its header says "MVP".

So weave was the executable form of the dialect idea: a graph whose steps are scripts, small
models writing in a constrained grammar, or the frontier, each step verified. The pieces now
exist apart: `ActionPlan` trees and their proofs in daisugi, the router for per-step models,
pathways as the scripty steps, and dialects as the constrained grammar. weave is where they were
meant to meet. grove's daemon half became coppice; its worktree per shoot and "the gate as a game
event" now live in coppice's tasks and asks.

## A tree of agents, each edge proved

sprig's main user is an agent, not a person. When a parent agent starts a child sprig, the
child's envelope must fit inside the parent's, proved by the subsumption check that already
guards skill delegation. Permissions can only shrink down the tree. coppice is the human's window
onto the tree; sprig is the unit it is built from; pi with the daisugi extension stays the
harness humans type into. **Open** until sprig resumes.

## Ranking is a primitive

"Given N attempts at one task, rank them, with a confidence" belongs in daisugi beside verify.
It is lexicographic:

1. Hard constraints eliminate: out of envelope, a failed proof, a failed required test.
2. Measured scores rank the rest: tests passed, tokens, time, size of the change.
3. Preferences break ties: model judges (cheap, pairwise) and the owner's picks (expensive,
   trusted most), combined with a Bradley-Terry or Elo ensemble. OpenHearth's eloEngine is
   prior art: Elo ensemble, Kendall tau for convergence, cycle checks for an inconsistent judge.
4. It asks the human only the most informative pair, and stops when confident.

The router learns from rankings, the garden's A/B test promotes with them, a parent sprig picks
among its children with them, and coppice shows them as an arena. A diff viewer and a "see no
code" outcome view are views on top.

## Token saving

- The August survey and its mapping (`docs/research/token-saving-landscape-*.md`) stand:
  verification is the missing column in every router; a pathway removes a model call, which
  beats making the call smaller.
- **Router design:** `design-router.md`. Cheap first with the verifier escalating; the frontier
  plans and cheap models do the steps; a chooser learned from the owner's journal; honest
  measurement first.
- **Grafts (from Spotify's Portal and shunt, September 2026).** A fourth gate verdict,
  **rewrite**, beside allow, deny and ask: "do this cheaper call instead". Rules are data. Z3
  proves each rule at install with the envelope subsumption proof we already have (a delegate
  read adds a network effect to the worker, so the envelope must grant it; the local-first
  default is a local worker). The garden proposes rules from the journal, runs them in audit,
  and promotes one only when it is safe and measurably saves tokens. The router picks the worker
  model. This amends the mapping doc's rule that the assurance layer never edits requests: a
  graft edits a tool call, never the model request, so the prompt cache is kept, and each graft
  is proved and logged. **Open:** write the grafts design after a fresh research pass (Spotify,
  and which harness hooks can rewrite tool input).
- Plans as trees: the `ActionPlan` step types (task, agentic, shell, file, network, skill, mcp)
  already form verified trees; a `skill` step holds a whole plan. Missing: the router filling
  each step's model, a runner outside Python, and plans shown on the floor. weave was meant to be
  that runner. **Open** (sprig and weave are on hold with the owner).

## What the labs say (September 2026)

- **OpenAI, harness engineering:** mechanical enforcement (structural tests, custom linters),
  AGENTS.md as a map, scheduled "garbage collection" agents, agent-legible observability.
- **Anthropic, long-running harnesses:** an initializer agent, a JSON feature list whose
  pass/fail flags are the ground truth, a progress file, git discipline, end-to-end browser
  tests, one feature at a time.
- **xAI, Grok Build:** up to 8 parallel agents in git worktrees, plan, review, approve, hooks and
  MCP, a headless CI mode, and a promised Arena Mode that ranks competing outputs before a human
  reviews them.

The common pattern: the harness is the product, checks live outside the model, agents run in
parallel worktrees, the human reviews. openDaisugi checks actions before they run; the labs
check outputs after. The gap to close: output checks. A pass/fail feature list is the missing
label for the router's learning and the missing "done" signal for a coppice task.

## Human review at speed

The owner reviews code closely at work and does not want to see code at all at home. The first
user sketch (a parent who wants agents to build her ideas without touching a laptop) is the
same wish. Two poles, one ramp:

- **See no code:** review outcomes, not diffs. Screenshots, a running preview, the feature list
  turning green, a one-line summary of each change.
- **See the code:** fast diffs and side-by-side arena outputs.
- **Between them:** ranked human feedback. When several agents or models attempt the same task,
  the owner picks the better of two, one pair at a time. The eloEngine in OpenHearth (Elo
  ensemble, Kendall tau, cycle checks) is prior art for turning those picks into a ranking. The
  picks become labels for the router and the garden. This could be a default plugin in coppice
  or sprig. A full diff viewer like GitHub's may be too heavy to ship; a pairwise "which is
  better" screen is light. **Open.**

## The worry, and the answer

The owner's worry: we built too much and too little. The UX may not hold 10 projects, the gate
may block too much, the router may not save tokens. Every number so far comes from synthetic
cases; they prove correctness, not usefulness. The Omarchy goal ranked UX first, and the last two
days were mostly ports.

The answer: a **dogfood week.** Keep one port job running in the background. Measure the gate's
false-deny rate from its audit log, meter the gateway on real traffic, drive coppice across real
projects with a friction log, and fix the top three pains before any new design.
